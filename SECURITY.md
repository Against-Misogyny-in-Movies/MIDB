# Security

What the site stores and sends is in [PRIVACY.md](PRIVACY.md). This file names the code behind each point.

## Network

- **Server-side requests:** the server calls TMDB (`api.themoviedb.org`, and `image.tmdb.org` for the image route) and Does the Dog Die (`www.doesthedogdie.com`), with keys that exist only on the server (`#lib/server/integrations/`). Nothing under `#lib/server/` can be imported by client code; SvelteKit enforces the boundary at build time.
- **Source sync:** the sync scripts (`db/scripts/sync/`, run by a person or a scheduled job, never by a page visit) fetch public files from `www.unconsentingmedia.org`, `bechdeltest.com` and `files.tmdb.org`, and call TMDB's `/find` with `TMDB_API_TOKEN` when one is set. They send the `MIDB-sync` User-Agent (the `/find` lookups too) and no reader data. They validate what they read before writing: a fetch or parse failure, a source with no rows, an unexpected shape, or a non-OK `/find` answer changes nothing and fails the run, and the Unconsenting Media sync also refuses a feed that would delete most stored entries. A database error part way through leaves the earlier batches applied, and the next run finishes the diff. They write to D1 through the Cloudflare API only with `--remote` and the `CLOUDFLARE_*` variables.
- **Browser requests:** the browser calls MIDB's own `/api/*` endpoints, including `/api/auth/*` for sign-in, and is sent to Google or Discord when a reader picks one of them. When a reader starts creating an account and a Turnstile site key is set, the browser also loads Cloudflare's script from `challenges.cloudflare.com` and sends it the check (`src/lib/components/auth/turnstile.svelte`); the server verifies the token with Cloudflare's siteverify (`src/lib/server/auth/turnstile.ts`). Posters come from MIDB's `/img/tmdb/` route, which fetches `image.tmdb.org` on the server (`src/routes/img/tmdb/[size]/[file]/+server.ts`); it fetches only a size in `TMDB_IMAGE_SIZES` and a file name that matches `TMDB_IMAGE_FILE` (`src/lib/media/utils/tmdbImage.ts`), and serves only an upstream `image/jpeg`, `image/png` or `image/webp`, so a request cannot choose another host or path. The font is served from `static/fonts`.
- **Caching:** public pages are cached by the CDN with a key that ignores cookies, so their loads never read the request's user (`src/lib/server/http/cache.ts`). The request hook makes any response without a `cache-control` header, or with a cookie, `private, no-store` (`src/hooks.server.ts`). Account data reaches the browser only through `private, no-store` responses: `/api/me`, `/api/auth/*` and the `/user` pages.
- **Authorization:** every endpoint and page that needs an account checks it with `requireUser` / `requireRole` (`src/lib/server/auth/guards.ts`). Roles are read from the database, never from the session. Sessions are Better Auth's (`src/lib/server/auth/create-auth.ts`): an `HttpOnly` cookie, with a signed five-minute cache of the session, so the request hook re-reads the user row for the ban and the role (`src/hooks.server.ts`). A ban deletes the user's sessions and the `session.create` hook refuses new ones. Sign-in has no passwords; a passkey stores only its public key, and Google and Discord sign-in is enabled only when its credentials are set.
- **Sign-in methods:** an account cannot remove its last sign-in method. The check counts linked accounts and passkeys together and runs on the server for both removal endpoints, which refuse a request with no live session in the database, whatever its cached cookie says (`src/lib/server/auth/last-method.ts`). A Discord sign-in links to an existing user only when Discord reports the email verified; only Google is trusted without that. The access and refresh tokens of linked accounts are stored encrypted with a key derived from `BETTER_AUTH_SECRET`. The Turnstile check on `/passkey/generate-register-options` applies only when there is no session, so a signed-in reader adds a passkey without it. `createAuth` refuses to start without `BETTER_AUTH_SECRET` unless the origin is localhost, because Better Auth's own check keys on `NODE_ENV`, which a Worker does not set. A user with no linked account, no passkey and no session, created more than `ORPHAN_AFTER_MS` ago (a sign-up that never got its passkey), is deleted when a person runs `pnpm db:cleanup:orphans` (`db/scripts/cleanup-orphans.ts`); from Phase 6 a scheduled job runs it.
- **Comments:** every comment write (a comment, an edit, a delete, a vote, a report) runs, in order, `requireUser`, a mute check on the freshly read user row, a per-user rate limit and zod validation of the JSON body when there is one; a comment's text has a length limit after trimming (`COMMENT_BODY_MAX` in `src/lib/media/utils/comments.ts`) (`src/lib/server/http/comment-request.ts`). A banned account is signed out by the hook, so it gets 401, and a muted one gets 403. Edit and delete are for the author only, a vote or report by a comment's author on that comment is refused, and a moderator action on a comment or an account is refused when the moderator may not act on the comment's author or the account (`src/lib/server/data/moderation-actions.ts`). A status change that lost a race with another request changes nothing and answers 409 or `invalid-state`. The moderation page's form actions each run `requireRole` (the hook also gates `/user/moderation`), then a per-user rate limit, then the query, and a comment action purges the title's list (`src/routes/user/moderation/+page.server.ts`). The public list never reads the user and sets no cookie; what is personal (votes, pending and rejected comments) comes from a `private, no-store` endpoint. Each multi-row write is one `db.batch`. Comments are returned as JSON and rendered by Svelte, which escapes text. A failed cache purge is logged and swallowed, so a stale list is bounded by its short edge TTL.
- **Rate limits:** search, username checks, the sign-in endpoints (`/api/auth/*`), the comment writes and the moderation actions are rate-limited with Cloudflare Workers rate-limit bindings (`src/lib/server/http/rate-limit.ts`, `wrangler.jsonc`). A limiter outage lets requests through.

## Supply chain

- **Dependencies:** `pnpm-lock.yaml` is committed, and CI installs with `--frozen-lockfile`.
- **CI:**
  - CI (`.github/workflows/tests.yml`) runs with a read-only token, so pull requests from forks cannot write to the repository or read secrets.
  - Every action is pinned to a commit SHA.
  - Dependabot (`.github/dependabot.yml`) opens weekly updates for packages and actions, which pass the same CI.
- **Secrets:** no secret is committed. `.env` and `.dev.vars` are ignored by git, `.env.example` holds placeholders only, and `wrangler.jsonc` holds bindings and non-secret values. Production secrets are set with `wrangler secret put`; server code reads them through `src/lib/server/env.ts`. The database is reached only by server code, through the `DB` binding. `CLOUDFLARE_API_TOKEN` (with `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_D1_DATABASE_ID`) is a local script credential for `--remote`: it can write to the production database, and it lives only in a contributor's gitignored `.env`.

## Reporting a vulnerability

Use the repository's Security tab, "Report a vulnerability". Do not open a public issue. Include what is affected (a page, an endpoint, a script, a dependency), how to reproduce it, and what it allows.

This is a volunteer project, so there is no fixed response time. Fixes go to `main`, which is what the site runs.
