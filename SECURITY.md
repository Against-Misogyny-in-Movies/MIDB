# Security

What the site stores and sends is in [PRIVACY.md](PRIVACY.md). This file names the code behind each point.

## Network

- **Server-side requests:** the server calls TMDB (`api.themoviedb.org`, and `image.tmdb.org` for the image route) and Does the Dog Die (`www.doesthedogdie.com`), with keys that exist only on the server (`#lib/server/integrations/`). Nothing under `#lib/server/` can be imported by client code; SvelteKit enforces the boundary at build time.
- **Source sync:** the sync scripts (`db/scripts/sync/`, run by a person or a scheduled job, never by a page visit) fetch public files from `www.unconsentingmedia.org`, `bechdeltest.com` and `files.tmdb.org`, and call TMDB's `/find` with `TMDB_API_TOKEN` when one is set. They send the `MIDB-sync` User-Agent (the `/find` lookups too) and no reader data. They validate what they read before writing: a fetch or parse failure, a source with no rows, an unexpected shape, or a non-OK `/find` answer changes nothing and fails the run, and the Unconsenting Media sync also refuses a feed that would delete most stored entries. A database error part way through leaves the earlier batches applied, and the next run finishes the diff. They write to D1 through the Cloudflare API only with `--remote` and the `CLOUDFLARE_*` variables.
- **Browser requests:** the browser calls MIDB's own `/api/*` endpoints, including `/api/auth/*` for sign-in, and is sent to Google or Discord when a reader picks one of them. When a reader starts creating an account and a Turnstile site key is set, the browser also loads Cloudflare's script from `challenges.cloudflare.com` and sends it the check (`src/lib/components/auth/turnstile.svelte`); the server verifies the token with Cloudflare's siteverify (`src/lib/server/auth/turnstile.ts`). Posters come from MIDB's `/img/tmdb/` route, which fetches `image.tmdb.org` on the server (`src/routes/img/tmdb/[size]/[file]/+server.ts`); it fetches only a size in `TMDB_IMAGE_SIZES` and a file name that matches `TMDB_IMAGE_FILE` (`src/lib/media/utils/tmdbImage.ts`), and serves only an upstream `image/jpeg`, `image/png` or `image/webp`, so a request cannot choose another host or path. The font is served from `static/fonts`.
- **Caching:** public pages are cached by the CDN with a key that ignores cookies, so their loads never read the request's user (`src/lib/server/http/cache.ts`). The request hook makes any response without a `cache-control` header, or with a cookie, `private, no-store` (`src/hooks.server.ts`). Account data reaches the browser only through `private, no-store` responses: `/api/me`, `/api/auth/*` and the `/user` pages.
- **Authorization:** every endpoint and page that needs an account checks it with `requireUser` / `requireRole` (`src/lib/server/auth/guards.ts`). Roles are read from the database, never from the session. Sessions are Better Auth's (`src/lib/server/auth/create-auth.ts`): an `HttpOnly` cookie, with a signed five-minute cache of the session, so the request hook re-reads the user row for the ban and the role (`src/hooks.server.ts`). A ban deletes the user's sessions and the `session.create` hook refuses new ones. Sign-in has no passwords; a passkey stores only its public key, and Google and Discord sign-in is enabled only when its credentials are set.
- **Sign-in methods:** an account cannot remove its last sign-in method. The check counts linked accounts and passkeys together and runs on the server for both removal endpoints, which refuse a request with no live session in the database, whatever its cached cookie says (`src/lib/server/auth/last-method.ts`). A Discord sign-in links to an existing user only when Discord reports the email verified; only Google is trusted without that. The access and refresh tokens of linked accounts are stored encrypted with a key derived from `BETTER_AUTH_SECRET`. The Turnstile check on `/passkey/generate-register-options` applies only when there is no session, so a signed-in reader adds a passkey without it. `createAuth` refuses to start without `BETTER_AUTH_SECRET` unless the origin is localhost, because Better Auth's own check keys on `NODE_ENV`, which a Worker does not set. A user with no linked account, no passkey and no session, created more than `ORPHAN_AFTER_MS` ago (a sign-up that never got its passkey), is deleted when a person runs `pnpm db:cleanup:orphans` (`db/scripts/cleanup-orphans.ts`); a daily job in `.github/workflows/deploy.yml` runs it.
- **Comments:** every comment write (a comment, an edit, a delete, a vote, a report) runs, in order, `requireUser`, a mute check on the freshly read user row, a per-user rate limit and zod validation of the JSON body when there is one; a comment's text has a length limit after trimming (`COMMENT_BODY_MAX` in `src/lib/media/utils/comments.ts`) (`src/lib/server/http/comment-request.ts`). A banned account is signed out by the hook, so it gets 401, and a muted one gets 403. Edit and delete are for the author only, a vote or report by a comment's author on that comment is refused, and a moderator action on a comment or an account is refused when the moderator may not act on the comment's author or the account (`src/lib/server/data/moderation-actions.ts`). A status change that lost a race with another request changes nothing and answers 409 or `invalid-state`. The moderation page's form actions each run `requireRole` (the hook also gates `/user/moderation`), then a per-user rate limit, then the query, and a comment action purges the title's list (`src/routes/user/moderation/+page.server.ts`). The public list never reads the user and sets no cookie; what is personal (votes, pending and rejected comments) comes from a `private, no-store` endpoint. Each multi-row write is one `db.batch`. Comments are returned as JSON and rendered by Svelte, which escapes text. Every new or edited comment passes `decideStatus` (`src/lib/server/moderation/`) before it is stored: a blocklist, then the model named by `MODERATION_MODEL` (`wrangler.jsonc`) with a structured verdict, then a pure policy. Any failure of the check (no key, timeout, refusal, malformed answer) holds the comment for a moderator, and the model's output is validated by a zod schema before use. The comment, title and parent comment reach the model only as tagged data in the user turn, with `<` escaped, and the system prompt is fixed. The prompt, policy and blocklist are public by design, so they are not a defence on their own: the rate limit, the body length limit, Turnstile on passkey sign-up, the moderator queue, report holds and bans are. `ANTHROPIC_API_KEY` and `MODERATION_EXTRA_TERMS` are secrets read per call; `MODERATION_DEV_AUTO_APPROVE` publishes comments that pass the blocklist when there is no key, and takes effect only when `PUBLIC_ORIGIN` is localhost. A failed cache purge is logged and swallowed, so a stale list is bounded by its short edge TTL.
- **MIDB community reports:** `PUT` and `DELETE` on `/api/titles/[kind]/[tmdbId]/reports` follow the same order (`authorizeWrite`, then zod) on the `RL_CONTENT_REPORT` bucket, and `POST …/reports/flag` ("Counts look wrong") on `RL_REPORT`; `GET …/reports/viewer` is `requireUser` and `private, no-store`. The body is validated against the vocabulary in `src/lib/media/utils/communityReports.ts`, "I watched this" must be true, and a Yes flag under sexual violence Not shown is refused. The public counts `GET` never reads the user. The counts leave out reports that are not `counted`, accounts younger than `REPORT_ACCOUNT_MIN_AGE_DAYS`, and muted or banned accounts. A moderator or administrator (`STAFF_ROLES`, `src/lib/media/utils/staff.ts`) is exempt from the age wait, the hold rules and the rate limit on these three writes (`authorizeWrite` with `staffExempt`); the guard and the mute check still run first, and staff accounts are trusted by role, not by the report's content. Three hold rules run on every save, an edit included, and hold a report for a moderator: it contradicts the title's Unconsenting Media entry, it is part of a burst on one title, or it comes from a busy new account (`src/lib/server/data/community-report-holds.ts`; the thresholds are in `communityReports.ts`). The write statement keeps a rejected report rejected, so a concurrent edit cannot undo a moderator. The moderation actions on community reports and count flags each run `requireRole`, then `RL_MODERATE`, then one `db.batch` that writes the status change and its log row, and then purge the title's counts after the batch succeeds, a failed purge logged and swallowed like the comments' (closing a "Counts look wrong" changes no counts); mute and ban purge the counts of every title the account reported (`src/lib/server/data/community-report-moderation.ts`, `moderation-actions.ts`).
- **Logs:** Workers Logs is on for both Workers (`observability` in `wrangler.jsonc`). Server code logs only failures (`console.error` / `console.warn` with the step that failed and the error), never a session, cookie, email or comment body.
- **Rate limits:** search, username checks, the sign-in endpoints (`/api/auth/*`), the comment and community-report writes and the moderation actions are rate-limited with Cloudflare Workers rate-limit bindings (`src/lib/server/http/rate-limit.ts`, `wrangler.jsonc`); the community-report writes skip the limit for moderators and administrators. A limiter outage lets requests through.

## Supply chain

- **Dependencies:** `pnpm-lock.yaml` is committed, and CI installs with `--frozen-lockfile`.
- **CI:**
  - CI (`.github/workflows/tests.yml`) runs with a read-only token, so pull requests from forks cannot write to the repository or read secrets.
  - Every action is pinned to a commit SHA.
  - **Deploys** (`.github/workflows/deploy.yml`): production deploys on a push to `main`, and a pull request whose branch is in this repository deploys the separate preview Worker, which has its own D1 database and rate-limit namespaces and never touches production data. Every job that holds a Cloudflare token runs only on the canonical repository, and `pull_request_target` is never used, so a fork's pull request gets tests and no secrets. The rule and the steps are in `.claude/rules/deploy-standards.md` and `docs/architecture.md`, Deploy.
  - **Who holds what:** `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID` and `TMDB_API_TOKEN` are GitHub secrets, passed only to the steps that need them. The Worker's own secrets (`BETTER_AUTH_SECRET`, the OAuth, Turnstile, Anthropic and moderation values) are set with `wrangler secret put` by a maintainer and are never in the workflow.
  - Dependabot (`.github/dependabot.yml`) opens weekly updates for packages and actions, which pass the same CI.
- **Secrets:** no secret is committed. `.env` and `.dev.vars` are ignored by git, `.env.example` holds placeholders only, and `wrangler.jsonc` holds bindings and non-secret values. Production secrets are set with `wrangler secret put`; server code reads them through `src/lib/server/env.ts`. The database is reached only by server code, through the `DB` binding. `CLOUDFLARE_API_TOKEN` (with `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_D1_DATABASE_ID`) can write to the production database: it is a local script credential for `--remote` in a contributor's gitignored `.env`, and a GitHub secret held by the deploy, sync and cleanup jobs.

## Reporting a vulnerability

Use the repository's Security tab, "Report a vulnerability". Do not open a public issue. Include what is affected (a page, an endpoint, a script, a dependency), how to reproduce it, and what it allows.

This is a volunteer project, so there is no fixed response time. Fixes go to `main`, which is what the site runs.
