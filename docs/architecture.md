# MIDB — Architecture Reference

> The detail pages are built around a **multi-source metrics model**: a `titles` spine (movies and TV), synced source-of-truth tables (`title_bechdel`, and `title_um` bindings into the **spine-independent UM catalogue** `um_source`) and a **live-fetched, streamed** Does-The-Dog-Die client. Both **movies and TV series** are supported (`/movie/[movieId]`, `/tv/[seriesId]`). Each metric is planned to display **two scores side by side**: the original authoritative source and a **MIDB community rating**; titles will also have a **comments section**. The per-metric community tables and `comments` exist; their write path is the next milestone (see _Known gaps_).
>

## What it is

**MIDB (Movie Information Database — working title)** is a web platform for displaying movies and TV series through a **diversity / content-safety lens**. The audience is survivors and trauma-sensitive viewers, and people who care about women's representation — people deciding whether a title is safe to watch. Users find a title and see how it scores across structured **metrics** — formal tests and content advisories for representation and harm. Three sources are wired today: the **Bechdel Test**, **Unconsenting Media** (sexual-violence advisories), and **Does The Dog Die** (crowd-sourced trigger tags).

Title facts (poster, overview, release/air date, credits, seasons) are **not stored** — they're fetched live from **TMDB** on each request. What _is_ stored locally is a thin spine (`titles`, keyed by `(kind, tmdb_id)` for films and series) plus **synced, authoritative metric data** (Bechdel rating, UM advisory flags) and a **spine-independent UM catalogue** (`um_source`) that powers the runtime disambiguation picker. DDD data is fetched live and streamed, not persisted.

Each metric is designed to show **two scores side by side**: the original authoritative source (Bechdel, UM, DDD) and a **MIDB community rating** contributed by users who have watched the film. Movies will also have a **comments section** for viewer context and discussion. Community ratings and comments are the next major feature milestone: the per-metric community tables and `comments` exist (remediation PR 4), and the `/user/*` area already has the profile editor and the (empty) rating and comment history views.

## High-level data flow

```
                  ┌────────────────────────────────────────────┐
   Browser  ──►   │  SvelteKit server (hooks + load functions)  │
                  └──────┬──────────────┬──────────────┬────────┘
                         │ (via #lib/server/cache: Cache API  │
                         │  + per-isolate memory)             │
            cached fetch┌─▼────────┐ ┌───▼──────┐ ┌─────▼───────┐
                        │  TMDB    │ │   DDD    │ │  D1 (SQLite)│
                        │  API v3  │ │   API    │ │  (Drizzle)  │
                        └──────────┘ └──────────┘ └─────────────┘
                         ▲            ▲ (streamed,   ▲
              poster / overview /     │  cached 1h)  │  synced source data:
              credits / imdb_id    trigger tags    titles + Bechdel + UM
              (cached 24h)

   Auth:  Browser ⇄ Hanko Cloud (web components + JWT cookie)
          hooks.server.ts verifies the `hanko` cookie via remote JWKS
   Migrations: `wrangler d1 migrations apply` (`pnpm db:migrate:local` / `db:migrate:remote`)
               from `db/migrations`; the server never migrates on boot
```

- **Entry point** is the landing page at `/` (hero + search UX). The hero search is a **live, inline TMDB search**: typing queries a server proxy (`/api/search`, TMDB `search/multi`) and renders a results dropdown in place — there is no `/search` page. Results carry a `mediaType` (`movie`/`tv`) and route to the matching detail page.
- **Title identity** flows by **TMDB id** through the URL (`/movie/[movieId]`, `/tv/[seriesId]`), but the internal join key across metric sources is **`imdb_id`** (the Bechdel/DDD key). On a detail-page load the live TMDB title is resolved to a local `titles` row via **read-only** `getTitleRow(kind, ref)` (matching on `(kind, tmdb_id)` then `imdb_id`); a GET never mutates the DB. Movies and series share the TMDB numeric id space, so `kind` is part of the key; there are no synthetic ids.
- **Metric data** comes from three places: **Bechdel + UM** are stored in D1 and rendered server-side (SSR); **DDD** is fetched live from its API and **streamed** so a slow external call never blocks first paint. (Bechdel is movie-only; series surface UM + DDD.)
- **Caching.** TMDB title fetches (`getMovie`/`getSeries`), TMDB search (`searchTitles`) and DDD lookups go through `#lib/server/cache` so repeat visits to a title skip the external round-trip — the dominant source of detail-page latency. The backend is the Cache API behind a per-isolate memory level (see _Server cache_). Public page loads set `PUBLIC_PAGE` (the landing, whose films are random per request, sets `PUBLIC_NO_STORE`), `/api/search` sets `PUBLIC_SEARCH` and `/img/tmdb/*` sets `PUBLIC_IMAGE`, so Workers Caching serves repeat requests without running the Worker (see _Caching policy_).
- **Auth** is entirely Hanko's; the app verifies the JWT cookie server-side (claims only, no DB) to gate `/user/*`, and server-rendered public pages never depend on the user (see _Auth flow_).

**Key structural choices:**

- The database layer (`db/`) sits _outside_ `src/`, exposed to app code as `#db/*` (package.json `imports`). App code imports `db` from `#lib/server/db.ts` (a lazy proxy over the `DB` binding); scripts call `openScriptDb()` from `db/scripts/lib/db.ts`. Both build it with `createDb` from `db/client.ts`, which reads no env itself.
- **Shared server logic does not live inside route folders.** Anything two routes both need (DB queries, external API clients) lives under `#lib/server/`; route folders keep only their route files (`+page.svelte` / `+page.server.ts` / `+server.ts`).

### File-organisation conventions

- **`#lib/server/**` is the server-only boundary.** SvelteKit fails the build if any client-reachable code imports from it. Secrets (`TMDB_API_TOKEN`, `DDD_API_KEY`, …) come from `#lib/server/env.ts`and DB access lives here only.`data/`= D1;`integrations/` = external HTTP clients.
- **Components for types, never routes.** A component that needs a `Movie`/`Series`/`TriggerTag` type imports it from `#lib/media/types/*` — `media/types/ddd.ts` re-exports DDD types from `integrations/ddd-types.ts` (not `ddd.ts`) as **types only** (erased at build, so no server runtime leaks into the client bundle). Components no longer reach back into `routes/.../`.
- **`ui/` vs domain.** Title-specific UI lives in domain folders (`movies/*`, `landing/`, `search/*`, …). `ui/` holds generic primitives with at least two real consumers: today only `ui/badge.svelte`.
- **Imports use `#lib` and `#db`**, the subpath imports in package.json (`#lib/*` → `src/lib/*`, `#db/*` → `db/*`), with explicit extensions (`#lib/media/utils/format.ts`, `#lib/components/ui/badge.svelte`); relative `./` is reserved for same-folder siblings. The Node-run scripts under `db/` and `scripts/` (and what they import: `db/client.ts`, `db/schema/*`, `db/lib/*`) use relative `.ts` imports, so they stay free of the app's imports map, and `erasableSyntaxOnly` keeps their syntax strippable.
- **Tests are co-located in a `__tests__/` subfolder** at each location (the `unit` project globs `src/**/*.{spec,test}.{js,ts}` and `db/**/*.spec.ts` at any depth). Specs that touch the database are named `*.db.spec.ts` and run only in the `db` project (`pnpm test:db`); the `unit` project excludes them and mocks `#lib/server/db`. Playwright e2e specs live in top-level `e2e-tests/`.

## Styling & theming

The styling system is **Tailwind CSS v4, CSS-first**. There is no JS theme config in the build path — the source of truth is `src/app.css`.

- **Entry & tokens.** `app.css` begins with `@import "tailwindcss"`. Build-time design tokens are declared in a `@theme { … }` block. Semantic _colors_ are exposed through **`@theme inline { --color-*: var(--*) }`** so utilities re-resolve at render time and a theme switch re-cascades without rebuilding.
- **Design-token system.** One definition per token with `light-dark()`: `--surface`, `--surface-raised`, `--surface-sunken`, `--ink`, `--ink-muted`, `--border`, `--border-strong`, `--brand` / `--brand-strong` (the project violet: the main action, links, focus, active states, the women data series), `--on-brand` / `--on-ink` (text on filled violet or ink), `--brand-wash` (8% lilac plate), `--src-bechdel` / `--src-um` / `--src-ddd` / `--src-tmdb` (four violet shades, one per source), `--accent` (suffragette green), the gender series `--seg-*`, status `--success` / `--warn` / `--danger` / `--info` with `-soft` fills (`--success` is `--brand`, so a good value stays violet; caution is copper, harm a darker raspberry, apart in lightness as well as hue so colour-blind readers can tell them apart), `--secondary-soft`, and elevation `--shadow-subtle` / `--shadow-md` / `--shadow-float` / `--shadow-brand`. Every solid status token passes 4.5:1 on its soft fill and on `--surface` in both themes. Type: `--font-display` **Inter Tight** (Google Fonts, 600/700, loaded in `app.html`) and `--font-body` / `--font-mono`, the system UI and mono stacks; `body` is tracked `-0.02em`. Shared classes in `app.css`: `.display` (Inter Tight 700), `.label`, `.link`, `.num`, `.card` (hairline 12px container), `.btn` + `--brand` / `--ink` / `--ghost` / `--pill`, `.disk` (icon disk: `--hue`, `--disk`), `.highlight` (coloured text over a highlighter stroke; its colour comes from a `.tone-*` class: `pos` / `mid` / `neg` / `neutral` mirror the badge tones, `bechdel` / `um` / `ddd` / `tmdb` the source shades), `.chip` (30px hairline pill for secondary links and the hero pager). Base layer themes focus rings, selection, caret, scrollbars, `select` and the Hanko elements. The look follows a pinned reference (Podscan.fm) on MIDB's palette: see `DESIGN.md`.
- **Theme switching.** `:root { color-scheme: light dark }` makes `light-dark()` follow the system; `:root[data-theme='light'|'dark']` pins `color-scheme` (manual override via the theme toggle, written to `document.documentElement.dataset.theme`).
- **Fonts.** Inter Tight is self-hosted: `@font-face` rules in `app.css` for the 600 and 700 woff2 files in the latin, latin-ext and vietnamese subsets (each with the package's `unicode-range`, so a subset downloads only for titles that use its letters; `font-display: swap`), the files in `static/fonts/`, and a `<link rel="preload">` for each latin file in `app.html` (only those: the landing's 600 sentence would otherwise shift layout when its file arrives). - **No `tailwind.config.js` and no PostCSS config.** Tailwind v4 reads everything from `app.css`.

## Copy & voice

User-facing copy follows a small house style. Apply it when writing or editing any visible text (page content, taglines, labels, notes); it does not govern code comments, `<title>` tags, or commit messages.

- **Matter-of-fact register.** State what a thing is and what happens, plainly. No marketing/salesperson tone, no rhetorical questions ("Want the short version first?"), no reader flattery or persuasion ("the only interest it serves is yours"), no hedging filler ("just", "the gist", "roughly where it stands"). The `/resources` page is the reference for the target voice: declarative, concrete, sourced.
- **Third person everywhere.** Address the reader in the third person ("the page lists the possible matches", "a reader"), not the second ("you can pick"). The landing page follows the same rule since the copy pass: its old motto ("Know before you watch") was replaced by a plain statement of what the site covers.
- **Essentials only.** Each fact once, in the fewest words that keep it. No taglines, no intros restating headings, no template subheadings, no stock phrasing ("at a glance", "distilling", "so you decide"). `/resources` was rewritten to this standard: one short lede, then plain paragraphs per source, with subheadings only for the two verdict axes.
- **Terminology.** film / series (not movie / TV), verdict, warning (DDD), flag and concern (UM), source, Bechdel Test. Sentence-case labels.
- **No em dashes (—) in copy.** Restructure instead: split into separate sentences, or use a colon when a list/expansion follows. En dashes (–) are correct in number and relationship ranges (`0–3`, `adult–teen`) and stay.
- **Claims must be code-backed.** Anything asserted to the user (privacy properties, how a metric is computed, thresholds) must match the code. The verdict-card explainer mirrors `verdict.ts` (exact flag tiers and scoring thresholds); the landing privacy line was verified against the codebase (no trackers, analytics or ads). The copy pass removed two claims the code did not back: "ratings submitted by the MIDB community" (no rating UI exists yet) and DDD warnings being "sorted by margin of the vote and grouped by category" (the client does neither). When the code changes, update the copy.

## User & roles

Users are identified by the Hanko subject (`sub` claim in the JWT, a UUID stored as `text`). `hooks.server.ts` verifies the claims on every request (local crypto, no DB) and exposes `locals.getUser()`, which JIT-provisions the row via `getOrCreateUser` only when a route asks for it (memoised per request). Public pages never call it.

**Client shape:** the only user object that reaches the browser is `PublicUser` (`#lib/media/types/user.ts`: `username`, `avatarKey`, `role`, `displayName`), built by `toPublicUser` in `user-queries.ts`. `displayName` falls back username → email local-part → `"Account"` on the server, so the email stays server-side except on `/user/profile`. Loads never return a `UserRow`.

**Role enum (`user_role`):** `user` | `moderator` | `administrator`. Default `user`. Authorization always reads the DB role through `requireRole` (`#lib/server/auth/guards.ts`) — Hanko has no concept of MIDB roles. Promote via `pnpm db:seed:admin <email>`.

**Profile fields:** `username` (text, CHECK length at most 32, case-insensitive unique via `lower(username)` index, validated `^[a-z0-9_]{3,32}$` + reserved-name blocklist), `avatar_key` (text, CHECK length at most 48, validated against avatar registry), `email` (nullable — Hanko's claim shape varies by tenant version; `emailFromClaims` handles both string and `{ address }` object forms).

**`getOrCreateUser`** reads first: `SELECT` by id; on a hit it returns the row, and `UPDATE`s `email` only when the stored value is null and the claim has one. On a miss it runs `INSERT … ON CONFLICT (id) DO NOTHING RETURNING *`, then re-`SELECT`s if a concurrent first request won. Steady state is one primary-key read and zero writes. It never bumps `updated_at`; that column is only set in `updateProfile` for real edits.

## Database schema

The active schema spans `db/schema/titles.ts`, `sources.ts`, `auth.ts` and `community.ts`, with shared column sets in `columns.ts`. The barrel `db/schema/index.ts` re-exports every file, and `createDb` (`db/client.ts`) and `db/test/setup.ts` rely on it.

**Conventions:** every timestamp is an integer of epoch milliseconds (`timestamp_ms`); tables with `created_at`/`updated_at` use `timestamps()` from `columns.ts`, which fills both on insert and whose `$onUpdate` bumps `updated_at` on every Drizzle update (pin it with ``updatedAt: sql`${col}` `` when a write must not count as an edit). Write-once tables use `createdAt()`. Ids are `text` filled by `crypto.randomUUID()`. A column with a fixed set of values is `text({ enum })` plus an `enumCheck(name, column, tuple)` CHECK from `columns.ts`, so the values are written once in the exported tuple (`userRole`, `titleKind`, `commentStatus`, `syncSource`). SQLite does not enforce `text(n)`, so a length limit is a `length(col) <= n` CHECK (`titles.title` and `clean_title`, `user.username` and `avatar_key`). Booleans are `integer({ mode: 'boolean' })`. The nine UM flag columns are defined once in `umFlagColumns()`. There are no `0` sentinels: unknown years and missing ids are `NULL`. D1 limits the bound parameters per statement (`D1_MAX_PARAMS`), so every bulk write goes through `chunkForD1` (`db/lib/chunkForD1.ts`), and D1 has no `BEGIN`: `db.transaction()` fails, and `db.batch()` is the atomic unit.

### Tables (active)

**`titles`** (`titles.ts`) — the spine for movies **and** TV; synced from the Bechdel Test, ids backfilled from TMDB.

- `id` text PK (UUID), `kind` text `movie`|`tv` NOT NULL (CHECK), `tmdb_id` integer nullable, `imdb_id` text nullable **unique**, `title` text (CHECK length at most 255), `clean_title` text (CHECK length at most 255; output of `normalizeTitle()`, the UM match key), `year` integer nullable (**NULL = unknown**), `popularity` real nullable (TMDB's popularity score, NULL until a sync has seen the title), `popularity_at` timestamp nullable, `created_at`, `updated_at`.
- **Unique index `titles_kind_tmdb_idx` on `(kind, tmdb_id)`**: the natural key, because TMDB movie and TV ids share a numeric space (movie 1399 and TV 1399 coexist). SQLite treats NULLs as distinct in a unique index, so rows without a TMDB id coexist. IMDb ids are globally unique across movies and series, so `imdb_id` has a plain unique. **Index `titles_popularity_idx` on `popularity`** serves the landing's ranking (`getPopularRatedFilms`; SQLite sorts NULLs last in descending order).

**`title_bechdel`** (`sources.ts`) — synced, **1:1 with a title**.

- `title_id` text **PK** → `titles.id` (cascade), `bechdel_id` integer, `rating` integer (**CHECK 0..3**), `created_at`.

**`um_source`** (`sources.ts`) — spine-independent **UM catalogue**; every movie and TV row from the UM source.

- `um_id` integer **PK**, `clean_name` text, `clean_title_key` text (year-stripped normalized key, the lookup index), `year` integer nullable (NULL = unknown), the 9 flag columns (`umFlagColumns()`), `comment` text, `source_updated_at` timestamp nullable (the feed's own `updatedAt`).
- **B-tree index `um_source_clean_title_key_idx` on `clean_title_key`** — `getUnconsentingCandidates` queries this column on every media page with no seeded UM binding (the common case); without the index that's a full table scan.
- Synced by `db:sync:um` for **all** UM movie/TV rows regardless of whether a title matches. Enables runtime candidate lookup without re-reading the feed.

**`title_um`** (`sources.ts`) — synced, **1:1 with a title**; the resolved UM binding, **by reference only**.

- `title_id` text **PK** → `titles.id` (cascade), `um_id` integer → `um_source.um_id`, `created_at`.
- The flags are read through the join (`getUmEntry`), so a UM sync is reflected immediately and there is one row shape (`UmEntry`). Matched by `clean_title` at sync time using a year-aware policy (see Source sync). User choices are never persisted (see UM Disambiguation below).

**`source_sync`** (`sources.ts`) — one row per synced source (`bechdel`, `um`, `popularity`): `source` text PK (CHECK), `last_success_at` timestamp, `rows_changed` integer. Written by each sync on success (`stampSync`); nothing reads it yet.

**`user`** (`auth.ts`) — Hanko-sub PK. `id` text (Hanko `sub`), `email` nullable, `role` text `user`|`moderator`|`administrator` default `user` (CHECK), `username` text(32) nullable, `avatar_key` text(48) nullable, `timestamps()`. Unique index on `lower(username)` (case-insensitive, NULLs don't collide). Index on `role`.

**Community tables** (`community.ts`) — empty; one table per metric shape so each can hold what it names. No write path yet (see Known gaps).

### Migrations

One SQLite baseline, `db/migrations/0000_init.sql` with its snapshot and journal, generated by drizzle-kit (`pnpm db:generate`, `dialect: 'sqlite'`, `drizzle.config.ts`). While the schema is still changing the baseline is regenerated (delete `db/migrations`, then generate) instead of stacked; once a database holds data, a change is a new migration, fixed forward and never rolled back by hand. Commit the generated SQL, snapshot and journal in the same change as the schema change; never hand-write or hand-edit a snapshot JSON. CI's `migrations` job runs `drizzle-kit generate --name drift_check` and fails if `db/migrations` changes. `db:generate` prompts (rename vs create) need a TTY; without one, run it as `script -qec "pnpm exec drizzle-kit generate" /dev/null` and answer the prompts.

Wrangler applies the files (`wrangler d1 migrations apply`, `migrations_dir` in `wrangler.jsonc`): `pnpm db:migrate:local` for the local database in `.wrangler/state` and `pnpm db:migrate:remote` for the deployed one. Each file is applied atomically and a failure stops the run. Foreign keys stay on (`.claude/rules/code-standards.md`, Database, says what a table rebuild sets). **Boot does not migrate.** The `drizzle.config.ts` D1 HTTP credentials (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID`, `CLOUDFLARE_API_TOKEN`) are read only when all three are set.

## Source sync

The Bechdel Test, Unconsenting Media (UM) and TMDB popularity are read from the sources' public files by the scripts in `db/scripts/sync/`; nothing from them is committed to the repository. The parsers are pure functions in `db/lib/sources/` (`parseUmFeed`, `parseBechdelYearPage`, `parseBechdelRss`, `readTmdbExport`) with every selector in one place, unit-tested against trimmed real responses in `db/test/fixtures/`. Each sync exports its core as a function taking `(db, source, options)`; the Node entry point (`if (isMain(import.meta.url))`) goes through `runSync` (`db/scripts/sync/lib/args.ts`), which opens the database with `openScriptDb(parseTarget(argv))` from `db/scripts/lib/db.ts`, closes it, and turns a failure into a non-zero exit. The database is the local D1 by default (wrangler's `getPlatformProxy`, in `.wrangler/state`), or with `--remote` the deployed one through `drizzle-orm/sqlite-proxy` over D1's REST `raw` endpoint (`db/scripts/lib/remote-d1.ts`, tested with a mocked `fetch`; not run against a live account). `--fixtures` swaps the live sources for the fixtures (`fixtureSources()` in `db/scripts/sync/lib/sources.ts`), so a run works offline; it always sweeps.

Every request carries the `MIDB-sync` User-Agent, a timeout and one retry (`fetchSource`). A sync reads and validates everything before its first write, and a source with no rows (or a changed shape) throws, so a failed run changes nothing and does not stamp `source_sync`. Writes are diffs: a run writes only rows that differ, so an unchanged source writes nothing. Each bulk write is split with `chunkForD1` into statements of at most 100 bound parameters, grouped with `db.batch` (`runBatches`); a run that stops part way is finished by running it again. A successful run stamps its source in `source_sync` with the time and the rows changed.

1. **`db:sync:um`** (`sync-um.ts`) — fetch `https://www.unconsentingmedia.org/list.json` (about 26 MB, no keys).
   - `parseUmFeed` keeps the items whose `itemType` is `movie` or `TV show`, validates them with zod, and maps the nine flags. It derives a `(titleKey, umYear)` pair per item using **`stripTrailingYear`** (UM's `cleanNameArticles` often embeds the year: `"wuthering heights 2026"`); UM's `yearOfRelease = 0` becomes NULL. `source_updated_at` is the feed's `updatedAt`.
   - Upserts `um_source` rows that are new or whose `updatedAt` is newer than the stored one; deletes rows missing from the feed, removing their `title_um` bindings first (`um_id` has no cascade).
   - Recomputes the bindings for every UM film against the film `titles` and writes the difference, so a new or renamed item, or a film the Bechdel sync added, is bound on the next run. `matchUmFilm` applies the **year-aware policy**: (1) only one film with the key → bind (unambiguous); (2) several → bind the exact `(titleKey, umYear)` hit; (3) several, no year hit → unmatched (`ambiguous`). One UM film per title: the highest `um_id` wins. Only `(title_id, um_id)` is written to `title_um`. TV rows are never bound here; the runtime picker covers them.
   - Prints the counts and the unmatched films (the first 200) to the job log. It does **not** create `titles` rows from UM data.
2. **`db:sync:bechdel`** (`sync-bechdel.ts`) — the JSON API is gone (410), so the data comes from the `https://bechdeltest.com/year/<YYYY>/` pages and the feed of the last 50 additions, at one request a second.
   - The daily run reads the feed's years plus the current year and the two before. `--full`, and a database that has never synced, sweep every year from 1874. A year with no films has no page (404) and counts as empty; a page whose film count differs from the rows read throws.
   - Upserts `titles` (`kind: 'movie'`, keyed by `imdb_id`; title, `clean_title`, year) and `title_bechdel` (`bechdel_id`, rating). Nothing is deleted.
3. **`db:backfill:tmdb`** (`backfillTmdb.ts`) — resolve null `tmdb_id` on **movie** titles with an IMDb id via TMDB `/find/{imdb_id}`. Needs `TMDB_API_TOKEN`. `getOrCreateTitleRow` will also backfill once a write endpoint uses it.
4. **`db:sync:popularity`** (`sync-popularity.ts`) — stream TMDB's daily `movie_ids_*` and `tv_series_ids_*` exports (gzipped NDJSON, no auth, ready by 08:00 UTC; the day before is used when today's is not out) and update `titles.popularity` and `popularity_at` for titles that have a `tmdb_id`, when the score changed. The exports are read, not stored.

**`db:sync:all`** runs 1, 2, 3, 4 in order. The two TMDB steps are skipped with a notice when `TMDB_API_TOKEN` is unset, so the other two need no account; with `--fixtures` the backfill is skipped (it calls TMDB's API) and popularity reads the fixture exports. The UM bindings need the film `titles`, so when the Bechdel sync adds films, `db:sync:all` runs the UM sync a second time over the same feed to bind them. Re-running any step is safe.

**`db/lib/normalizeTitle.ts`** — two exports (the app imports it as `#db/lib/normalizeTitle`, the sync scripts relatively, so the matching key is one module):

- `normalizeTitle(title)` — lowercase, strip leading articles (en/fr/de/es/it), strip diacritics + punctuation, collapse whitespace. Must mirror UM's `cleanName` conventions.
- `stripTrailingYear(normalized)` — removes a trailing ` (19|20)\d\d` from an already-normalized string, returns `{ key, year }`. Used to handle the ~12% of UM rows whose `cleanNameArticles` embeds the year.

Both are covered by unit specs (`db/lib/__tests__/normalizeTitle.spec.ts`). `db/scripts/__tests__/sync.db.spec.ts` covers the sync against the fixtures: the upsert-only diff (a second run writes nothing), deletions removing bindings first, the Bechdel upserts, the popularity update, `source_sync` stamping, and a source with no rows failing with nothing deleted.

## Detail pages (`src/routes/movie/[movieId]/`, `src/routes/tv/[seriesId]/`)

The flagship pages. Server-rendered for DB metrics, **streamed** for the live DDD call. Movies and series share one loader (`loadTitle`) and one client page-state class (`TitleView`); they differ only in which TMDB call runs and which metrics apply.

**Server (`+page.server.ts`, both pages):**

```ts

return loadTitle('movie', params.movieId); // or loadTitle('tv', params.seriesId)
```

**`#lib/server/titles/load-title.ts`** — `loadTitle(kind, tmdbId)` (overloaded, so the movie page gets `media: Movie` and the TV page `media: Series`):

1. `getMovie` / `getSeries` (TMDB, cached via `#lib/server/cache/index.ts`, TTL in `integrations/tmdb/client.ts`);
2. `getTitleRow(kind, media)` — read-only; `null` if the title was never seeded (GET routes never call `getOrCreateTitleRow`);
3. with a row: `getBechdel` (movie only, `null` for series) and `getUmEntry` in parallel; without one, both `null` and no DB round-trip;
4. no seeded UM binding → `getUnconsentingCandidates(media)`;
5. `getTriggerTagsLive(media.imdbId)` (movie) or `getTriggerTagsForSeries(media)` (tv), returned **un-awaited** so it streams.

**DDD live client (`#lib/server/integrations/ddd.ts`):** `getTriggerTagsLive(imdbId)` (movies, imdb lookup) and `getTriggerTagsForSeries(series)` (title text-search + tmdb/year match). Returns `TriggerTag[]` filtered to `yesSum >= noSum && yesSum > 0`, carrying season/episode scoping for series. Unit tests reset it with `clearCache()` from `#lib/server/cache`. **Client page state (`#lib/media/utils/titleView.svelte.ts`):** `new TitleView(() => data, kind)` in the page script. All `$derived` over the load data:

- `media`, `umCandidates`; `selectedUm` (writable `$derived` keyed on `media.id`: a pick overrides it, a title change resets it, no effect); `umData = umEntry ?? lone candidate ?? selectedUm`; `hasUmCandidates`; `flagCount` (`umFlagCount`);

Both `+page.svelte` files keep only markup and their own sections: the Bechdel criteria ladder (and its `.criterion-*` styles) on movies, the `DddEpisodeSelector` snippet on TV.

## UM Disambiguation

UM is the only source with no `imdb_id`, matched purely by normalized title. When a title has no seeded `title_um` binding, `getUnconsentingCandidates` resolves candidates from `um_source`:

| Title year known?          | Candidates                   | Outcome                                                                                                                     |
| -------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Yes                        | Exact year match found       | Return that one candidate → **rendered directly, no picker** (auto-match)                                                   |
| Yes                        | No candidate shares the year | Return the unknown-year (`year IS NULL`) entries, up to 5 (one → auto-match, several → picker); none → `[]` → **"No data"** |
| Unknown (no `releaseDate`) | Any                          | Return up to 5 candidates → **picker shown** (one → auto-match)                                                             |

**Nothing is persisted.** A user's pick lives only for the current page view — `TitleView.selectedUm` is a writable `$derived` keyed on `media.id`, so it resets on every title change. `TitleView` derives `umData = umEntry ?? autoUm ?? selectedUm`; the chip, section header, and flag list all read from `umData` so a picked candidate renders identically to a seeded binding.

**Why `um_source` exists:** `title_um` is a binding, keyed by `title_id`, so it only covers entries that _already matched_ a spine title. For ambiguous (same title, different year), TV, or spine-absent titles, `um_source` is the durable, re-queryable catalogue that doesn't require re-parsing the CSV per request. Bindings reference it, so both paths read one row shape.

**`UmEntry` type** (in `src/lib/media/utils/metrics.ts`, re-exported from `#lib/media/types/um.ts`) — `umId`, `cleanName`, `year`, `comment` + all 9 flag booleans. Seeded bindings and picked candidates both use it; the concern count is derived with `umFlagCount`, not stored.

**`umFlagCount(umData)` / `dddUrl(itemId)`** (in `src/lib/media/utils/metrics.ts`) — pure helpers shared by both detail pages and by the `umMetricSection` / `dddMetricSection` components. `umFlagCount` excludes `noRape` from the concern tally; `dddUrl` builds the deep-link or falls back to the DDD homepage.

## UM flag rendering

`UM_FLAGS` defines 9 flags. `noRape` is **inverted** — `true` means _no rape or sexual assault_ (a reassurance, not a concern). It is treated specially throughout:

- **Concern count** (`umFlagCount`, picker's `flagCount`) excludes `noRape`. The chip/status reads "0 concerns" when only `noRape` is true.
- **Flag list** — every flag is a row using the **shared circular marker** (see _Shared marker pattern_ below). `noRape === true` renders with `.um-flag--reassurance`: `ri-check-line` on `--success-soft`. All other present flags (`true`) → `.um-flag--present` with `ri-alert-line` on `--warn-soft`. Absent flags (`ri-subtract-line`) stay quiet (a transparent marker with a `--border` hairline) so present concerns lead the eye. The list is a column-gap-only grid (`minmax(17rem, 1fr)`, `gap: 0 --spacing-lg`). The UM note renders through `umComment.svelte`: notes over 360 characters (series notes run to thousands) clamp to four lines behind a "Show full notes" toggle.

## Shared marker pattern (metric row markers)

The metric sections in the detail page share **one visual language for per-item status rows**, so the stacked sections read as a family. Reuse it for any future metric checklist/ladder — don't invent a new marker shape.

- **Marker geometry.** A `1.375rem` round badge (`flex items-center justify-center rounded-full text-xs shrink-0`) holds a single Remixicon glyph or a step number. Rows are `flex items-center gap-sm`, `text-sm`, with `padding-block: var(--spacing-xs)` for the row rhythm.
- **States (tinted-fill convention).** _Active_ states fill the token's soft tint (`--warn-soft`, `--success-soft`, or `color-mix(in oklab, var(--brand) 14%, transparent)` for brand) with the solid token as glyph color. _Inactive_ states are a transparent marker with a `--border` hairline and an `--ink-muted` glyph. The active row's label goes `text-ink font-medium`; inactive stays `text-ink-muted`.
- **Token choice is semantic, not decorative.**
  - **Bechdel** (inline in the movie `+page.svelte`, `.criterion` / `.criterion-marker`) is a **cumulative ladder**: a met rung uses the **brand** tint + `ri-check-line`; an unmet rung stays quiet and shows `ri-close-line`. Brand, not a status tone: the overall `N/3` already reads from the section's status badge. No connector line.
  - **UM** (`umMetricSection`, `.um-flag` / `.flag-marker`) is an **independent flag set**, so no connector line. Present concerns are a real per-item signal → `--warn` tint; the inverted `noRape` reassurance → `--success` tint. Both correctly stay colored (the reassurance in `--success`, which is the brand violet).

## Live search (`src/lib/components/search/`)

- **`movieSearch.svelte.ts`** — `MovieSearchState` rune class: `query`, `results`, `activeIndex`, `loading`, `open`. - **`movieSearch.svelte`** — orchestrator: takes an optional `search` prop (a `MovieSearchState`) and otherwise instantiates one, wires `$effect(() => search.connect())`, click-outside dismiss, composes child components. Its listbox id comes from `$props.id()` (same on server and client). The landing page imports the component as `movieSearch.svelte`; the rune module is `movieSearch.svelte.js`. Mounted directly by the landing page.

## Server cache (`src/lib/server/cache/`)

A single cache fronts every external call so repeat detail-page visits skip the round-trip that dominates latency. It is not the page CDN: Workers Caching serves page responses (see _Caching policy_), and this store holds what the server fetches from TMDB and DDD and the landing's database queries.

- **API.** `getCached<T>(key, ttlMs, fetcher)` — returns the cached value or runs `fetcher`, stores it, and returns it. `ttlMs` may be a function of the fetched value, for a result that should live shorter (DDD's non-OK answers). A fetcher that throws stores nothing. Backend failures degrade to a cache miss (the fetcher still runs), so caching can never make a request fail — only slower. `clearCache()` (memory level and counters) is exposed for tests.
- **Backends** (`index.ts` picks one per call, because the dev server installs `caches` after the module loads):
  - **The Cache API** (`cache-api.ts`) where `globalThis.caches.default` exists (Workers, and `vite dev` through the adapter's platform proxy). Entries are JSON under the synthetic key `https://cache.midb.internal/<encoded key>` with a `Cache-Control` `max-age` of the entry's TTL and an expiry header. Values must survive `JSON.stringify` (one that does not is not stored). The write runs through `waitUntil`, after the response. The Cache API is per data centre, so a value cached by one isolate serves the next one there. A Cache API error is a miss.
  - **A per-isolate memory level** (`memory.ts`) in front of it: a bounded LRU with TTLs that answers repeats without a Cache API call, and takes only the TTL an entry has left when it is filled from the Cache API.
  - **Memory alone** where `caches` is missing (unit tests, plain Node).
- **Counters.** `incr(key, ttlMs)` adds 1 to a fixed-window counter and returns the count; the window starts on the first hit and the count starts over when it ends. Counters always live in the memory level (a separate `Map`, oldest window dropped first), so counters and cached values never evict each other; the Cache API has no atomic increment. They are the fallback of `rateLimit` where a bucket has no binding.
- **Keys** are namespaced: `tmdb:movie:v2:<id>`, `tmdb:series:v2:<id>`; `tmdb:search:v1:<lowercased query>`; `ddd:imdb:<id>`, `ddd:tmdb:<id>`; `catalogue:counts`, `catalogue:hero-pool:v2:<pool>` (the landing's database queries); counters `rl:<bucket>:ip:<address>` / `rl:<bucket>:user:<id>`. The TTLs are in `integrations/tmdb/client.ts`, `integrations/ddd.ts` and `data/catalogue.ts`. Cache API entries outlive a deploy, so a change to a cached value's shape bumps its key's version (`v2` in the TMDB keys).

## Auth flow (Hanko)

1. `/auth` renders `<hanko-auth>` → success event → `goto("/user/profile")`.
2. Hanko sets a `hanko` JWT cookie from JS (not httpOnly).
3. `hooks.server.ts` calls `verifyClaims` (`#lib/server/auth/hanko.ts`: **module-level** `createRemoteJWKSet`, created once so `jose` caches the JWKS) and sets `locals.claims` (payload or `null`). No DB access here.
4. `locals.getUser()` is lazy and memoised per request: on first call it runs `getOrCreateUser({ sub, email: emailFromClaims(claims) })` (`emailFromClaims` handles `string` and `{ address }` claim shapes); without claims it resolves `null`. Only `/api/me`, `/user/*` loads/actions/endpoints and the moderation gate call it.
5. The hook gates `/user` and `/user/*` (not `/users…` or `/username`) on **claims only**: no claims → `redirect(303, "/auth")`. `/user/moderation*` additionally awaits `requireRole(locals, ['moderator', 'administrator'], { page: true })` → `error(403)` for other roles.
6. **Guards** (`#lib/server/auth/guards.ts`): `requireUser(locals, { page? })` returns the `UserRow` or throws (`redirect(303, '/auth')` for page loads, `error(401)` otherwise); `requireRole(locals, roles, { page? })` adds `error(403)`. Every `/user/*` load, action and endpoint calls one; nothing reads a user off `locals` directly. Future form actions on public pages (e.g. `/movie/:id?/rate`) are not under the `/user` prefix, so the guard is their only check.
7. **SSR is user-agnostic.** There is no root `+layout.server.ts`; public pages carry no user data and are CDN-cacheable (see _Caching policy_). The `/user` layout returns `{ me: PublicUser }` with `private, no-store`.
8. **Client session** (`#lib/media/utils/session.svelte.ts`, imported as `session.svelte.js`): a module singleton with `status: 'pending' | 'anon' | 'user'`, `user: PublicUser | null`, and `hint`. The navbar calls `session.load()` on mount (root layout, so once per full page load; client navigations reuse it), which first sets `hint` from `document.cookie` containing `hanko=` and then fetches `/api/me`. The fetch is skipped when the session is already resolved (a full load of a `/user/*` page sets it from layout data first). `session.set(me)` comes from the `/user` layout data; `session.clear()` from logout. `set`/`clear` invalidate an in-flight fetch so a stale response cannot overwrite them. Writes are browser-only (the singleton would otherwise be shared across SSR requests); `hint` stays null through hydration so server and client markup match.
9. **Navbar auth slot** (`navbar.svelte`): a fixed-size box at the right edge of the bar (`8rem × 2rem`, `5.25rem` below `md`) with `aria-busy` while pending. SSR renders it empty; it then shows a placeholder from the hint (avatar circle, or "Sign in"), then the resolved state: the "Sign in" ink pill, or [moderation shield icon (md+ only)] + avatar + truncated `displayName` (name hidden below `md`). Nothing outside the slot moves (zero layout shift). Sign out lives on `/user/profile` and in `navbarMenu.svelte`, which reads the same session (`likelyUser`, role for the Moderation item). The moderation link is a convenience; authorization stays server-side.
10. `/user/profile` — profile view/edit (avatar + username). `/user/dashboard` — Hanko `<hanko-profile>` (account settings, `ssr=false`). `/user/comments`, `/user/metrics` — history views.
11. `logoutButton.svelte`: `await hanko.logout()` → `session.clear()` → `goto('/auth', { refreshAll: true })`, so the cookie is gone before any load re-runs.

## Caching policy

Workers Caching (`"cache": { "enabled": true }` in `wrangler.jsonc`) is the CDN. Cloudflare answers a hit before the Worker runs, so the code only sets headers. The key is path plus query plus the Worker version, and **cookies are not in it**: a deploy starts with an empty cache, and a response that depends on the reader would be served to everyone. A response with `Set-Cookie`, `private` or `no-store` bypasses the cache. A 200 with no cache header is cached by default, which is why the hook below exists. A policy applies to successful responses only: a load sets it after its lookup succeeds, because Kit applies `setHeaders` to the error page and the error `__data.json` too.

- `#lib/server/http/cache.ts` holds the policies as header sets, so they are greppable. A browser `Cache-Control` and an edge `CDN-Cache-Control` (which overrides `Cache-Control` at the edge only) are spread into `setHeaders`, or into a response's `headers`.
- `PUBLIC_PAGE` (a browser `Cache-Control` that revalidates, and an edge `CDN-Cache-Control` with stale-while-revalidate) is set by the `/resources`, `/movie/[movieId]` and `/tv/[seriesId]` loads; it applies to both the HTML and `__data.json`.
- `PUBLIC_NO_STORE` (`no-store`) is set by `/`: user-agnostic, but its hero films are random per request, so no cache keeps it. The expensive part, the film pool and the counts, is cached in the server cache (`catalogue.ts`).
- **Rule:** a load that sets `PUBLIC_PAGE` must not depend on the request's user (no `locals.getUser()`, no `locals.claims`). The cache key ignores cookies, so anything user-specific would be served to every visitor. Signed-in readers get the same cached HTML; the navbar hydrates from `/api/me`.
- `PUBLIC_SEARCH` (a browser and a longer edge TTL, the edge matching the server-side search cache) is set by `/api/search` on a successful result: the response is user-agnostic, so the edge absorbs repeated queries. An error answer (TMDB down, network failure) and a 429 carry no policy, so the hook makes them `private, no-store`.
- `PUBLIC_IMAGE` is set by `/img/tmdb/*` on a success: a poster file never changes under its name, and its TTL stays under TMDB's cap on caching its images.
- `PRIVATE_NO_STORE` (`private, no-store`) covers personalised responses: `/api/me` and every `/user/*` page (set in the `/user` layout).
- **Safe default** (`hooks.server.ts`, `withSafeCacheHeaders`): a response without `cache-control` becomes `private, no-store`, and a response with `Set-Cookie` is forced to `private, no-store` with any `CDN-Cache-Control` removed. Every branch that forces `private, no-store` also removes `CDN-Cache-Control` and `Cloudflare-CDN-Cache-Control`. The hook's own `/user` redirect to `/auth`, and the `/user/moderation` guard's redirect or error, are returned through it, not thrown, so they are never cached either. A route opts in to caching by setting a policy; forgetting to never publishes it.
- Workers Caching has no local emulation: `vite dev` and the built Worker under `pnpm preview` (`wrangler dev`) send the headers but cache nothing, so a hit can be checked only on a deployed Worker.
- **Rate limiting** (`#lib/server/http/rate-limit.ts`): `rateLimit(event, bucket, { userId? })`, where `bucket` is a `RateLimitBucket` naming a Workers rate-limit binding (`RL_SEARCH`, `RL_AVAILABILITY`, …; `limit` and `period` are in `wrangler.jsonc`). It throws `error(429)` when the binding says `success: false`. It keys on `userId` when the route already has the user (after `requireUser`), else on `event.getClientAddress()`, and never reads the user itself, so CDN-cached routes stay user-agnostic. Applied to `/api/search` (`RL_SEARCH`, after the empty-query short-circuit) and `/user/profile/availability` (`RL_AVAILABILITY`, per user). The binding counts per location and is eventually consistent, so a limit is approximate. A bucket with no binding (unit tests, a dev setup without one) falls back to the memory `incr` with the same numbers (`FALLBACK_LIMITS` in `rate-limit.ts`), per isolate. A binding error lets the request through.
- User-specific bits on a public page (e.g. a future "your rating") go in a separate uncached fetch, the same way the navbar uses `/api/me`.

`src/env.ts` marks every `PUBLIC_*` value `static`, so the app uses the build environment's value, inlined at build time; the `wrangler.jsonc` `vars` copies must match it, and changing one means a rebuild. The database is the `DB` binding, so `build` and `check` need no database and the server bundle contains no connection string. Secrets and bindings are read through `#lib/server/env.ts` over `cloudflare:workers`: `wrangler secret put` in production, `.env` in `vite dev` (the adapter's platform proxy loads it through Wrangler). `wrangler dev` (`pnpm preview`) reads `.dev.vars` when it exists, else `.env`; `.dev.vars` replaces `.env` rather than adding to it, and neither reads the process environment. `wrangler.jsonc` holds the bindings and non-secret `vars`, no secrets; `pnpm cf:types` regenerates `worker-configuration.d.ts` from it. `.env.example` is the committed template (allow-listed in `.gitignore`) and lists every variable. Its placeholders are valid enough for `pnpm check` and `pnpm build`, so a fresh clone and CI only need `cp .env.example .env`. Title pages need real `TMDB_API_TOKEN`/`DDD_API_KEY` values, and sign-in needs a real Hanko tenant. Deploys: not set up yet (the live plan, Phase 6).

**One package manager.** pnpm 10.28 locally and in CI: `package.json` declares `"packageManager": "pnpm@10.28.0"` and `"engines": { "node": ">=22.18" }` (the first Node 22 with type stripping on; `.npmrc`'s `engine-strict=true` enforces it), so CI installs exactly the `pnpm-lock.yaml` it tests. `pnpm.overrides` in `package.json` pins most direct dependencies to an exact version, so bumping a pinned one means editing its override (a `devDependencies` range bump alone changes nothing there; a dependency with no override follows its range); `pnpm.onlyBuiltDependencies` lists `esbuild` and `workerd`, the dependencies whose build scripts run (pnpm 10 blocks the rest). The old `npm install --legacy-peer-deps` was hiding a real peer conflict (Storybook 9 peers on Vite ≤7 and vite-plugin-svelte ≤6), fixed by moving to Storybook 10.6. No dependency is pinned to `latest`.

### Local run sequence

```bash
pnpm install
cp .env.example .env
pnpm db:migrate:local    # creates the local D1 in .wrangler/state
pnpm db:sync:all --local   # Unconsenting Media, Bechdel Test, TMDB ids and popularity (--fixtures: offline)
pnpm dev                # vite dev, with the Worker's bindings emulated
pnpm preview            # builds, then runs the built Worker locally with `wrangler dev` on 4173

pnpm test:db          # wipes .wrangler/test-state, migrates it from zero, runs *.db.spec.ts
```

### npm scripts

`dev` · `build` · `preview` (`pnpm build && wrangler dev`, local only, port 4173) · `check` · `typecheck` · `test` = `test:integration` + `test:unit` · `test:unit` = `vitest --project unit` (no DB) · `test:db` = `vitest run --project db` (local D1, no Docker) · `lint` / `lint:fix` / `format` (what they run: `package.json`, AGENTS.md) · `storybook` / `build-storybook` · `db:generate` · `db:migrate:local` · `db:migrate:remote` · `db:sync:um` · `db:sync:bechdel` · `db:sync:popularity` · `db:sync:all` · `db:backfill:tmdb` · `db:seed:admin` (`--username` or `--email`, case-insensitive promote to administrator). The `db:sync:*` and `db:backfill:tmdb` scripts take `--local` (default) or `--remote`; the sync scripts also take `--fixtures`, and `db:sync:bechdel` `--full`.

### CI (`.github/workflows/tests.yml`)

Runs on every PR, on pushes to `main`, and on manual dispatch. Every job but `commits` installs pnpm (the `packageManager` version) and Node 22 with the pnpm cache.

- **`static`**: `pnpm install --frozen-lockfile` → `cp .env.example .env` (so the static variables in `src/env.ts` resolve) → `pnpm check` → `pnpm typecheck` → `pnpm lint` → `pnpm build`.
- **`unit`**: `pnpm install --frozen-lockfile` → `pnpm test:unit --run`. Needs no secrets, `.env` or database, because unit specs mock `$app/env/*` and `#lib/server/db.ts`, and take `cloudflare:workers` from a stub.
- **`migrations`**: `pnpm exec drizzle-kit generate --name drift_check`, then fails (printing the status and diff) if `git status --porcelain db/migrations` is non-empty. Needs no DB. A drizzle-kit prompt also fails it (no TTY), which is the correct outcome.
- **`db`**: `pnpm test:db` on a local D1, with no service and no secrets. Global setup migrates the empty database from zero, so this job also proves the migration chain applies cleanly.
- **`e2e`**: skipped unless the repo variable `E2E_ENABLED` is `'true'`. It runs `db:migrate:local`, then `pnpm test:integration`; `playwright.config.ts` starts `pnpm preview` (build, then `wrangler dev`). A step writes `TMDB_API_TOKEN` and `DDD_API_KEY` into `.dev.vars`, which is where `wrangler dev` reads the Worker's secrets. It needs the secrets `TMDB_API_TOKEN` and `DDD_API_KEY` and the variable `PUBLIC_HANKO_API_URL` (static, read at build time). The Playwright report is uploaded on failure.

## Testing

Three layers, plus Storybook for component development. Specs live in a `__tests__/` folder next to the code they cover; Playwright specs in top-level `e2e-tests/`.

- **`unit`** (Vitest project, `jsdom`; `pnpm test:unit`): `src/**/*.{spec,test}.{js,ts}`, `db/**/*.spec.ts` and `scripts/**/*.spec.ts`, minus `*.db.spec.ts`. Needs no database, `.env` or secrets: specs mock `$app/env/*` and `#lib/server/db`, set secrets and bindings on the `cloudflare:workers` stub (`src/test/cloudflare-workers.stub.ts`), the TMDB/DDD `fetch` and `$app/*` as needed. Components render through `@testing-library/svelte` (`svelteTesting()` in `vite.config.ts`) with `@testing-library/jest-dom` matchers. Rune classes (`TitleView`, `EpisodeFilter`, `Session`, `MovieSearchState`, `DebouncedQuery`) are tested directly, with fake timers where they debounce. Endpoints are called as plain functions with a hand-built `RequestEvent` (`src/__tests__/api-*.spec.ts`).
- **`db`** (Vitest project, `node`; `pnpm test:db`): every `*.db.spec.ts` against a local D1 (Miniflare, through wrangler), with no Docker and no secrets. The project has its own config in `vite.config.ts` and does not extend the root one: the Svelte plugins add the `browser` export condition, which makes Miniflare load the browser build of `ws`. `db/test/global-setup.ts` wipes `.wrangler/test-state` and applies `db/migrations` to it with `wrangler d1 migrations apply --local` once per run (so the job also proves the baseline applies from zero); `db/test/setup.ts` opens that state with `getPlatformProxy`, binds the app's `db` to it (`bindDb`), deletes every table's rows in foreign-key order before each test and disposes the proxy after. `getPlatformProxy` takes the state root itself while the wrangler CLI adds a `v3` folder, so the setup passes `.wrangler/test-state/v3`. Files run serially (`fileParallelism: false`). "Never writes" checks use `db/test/writes.ts`, whose triggers log every write to a test-only table. Covers title resolution, sources, UM candidates, user queries, community-table constraints, the D1 behaviours the app relies on (`db/test/d1.db.spec.ts`) and the source sync on trimmed fixtures (`db/test/fixtures/`).
- **`e2e`** (Playwright, `pnpm test:integration`): `playwright.config.ts` runs `pnpm preview`, which serves the built Worker with `wrangler dev` on 4173 (Node's `vite preview` cannot load the built Worker: it imports `cloudflare:workers`). `landing.spec.ts` (hero, contribute link, theme toggle) and `navbarSearchOverflow.spec.ts` (mobile dropdown stays in the viewport, `/api/search` mocked with `page.route`). The CI job is gated on `E2E_ENABLED` because it needs real TMDB/DDD secrets.
- **Storybook** (`pnpm storybook`, `build-storybook`): `*.stories.svelte` with `@storybook/addon-svelte-csf`. Only the poster `image` story remains after the redesign deleted the unused primitives. Not run in CI.
- **Rule of thumb** (`.claude/rules/code-standards.md`, Testing): anything that touches the database gets a `*.db.spec.ts`; everything else stays in `unit` and mocks the DB. Moving a function means moving its spec's import too.

### Verification baseline

The baseline every finished task reports is `.claude/rules/code-standards.md`, Checking a change. CI runs the same jobs (see _CI_), plus the drift check (`pnpm exec drizzle-kit generate --name drift_check` → no change) and, on pull requests, the commit-subject check.
