# MIDB — Architecture Reference

> The detail pages are built around a **multi-source metrics model**: a `titles` spine (movies and TV), synced source-of-truth tables (`title_bechdel`, and `title_um` bindings into the **spine-independent UM catalogue** `um_source`) and a **live-fetched, streamed** Does-The-Dog-Die client. Both **movies and TV series** are supported (`/movie/[movieId]`, `/tv/[seriesId]`). Each metric shows its authoritative source; the per-metric community rating tables exist without a write path (see _Known gaps_). Titles have a **comments section** with AI-assisted moderation (see _Comments_).

## What it is

**MIDB (Movie Information Database — working title)** is a web platform for displaying movies and TV series through a **diversity / content-safety lens**. The audience is survivors and trauma-sensitive viewers, and people who care about women's representation — people deciding whether a title is safe to watch. Users find a title and see how it scores across structured **metrics** — formal tests and content advisories for representation and harm. Three sources are wired today: the **Bechdel Test**, **Unconsenting Media** (sexual-violence advisories), and **Does The Dog Die** (crowd-sourced trigger tags).

Title facts (poster, overview, release/air date, credits, seasons) are **not stored** — they're fetched live from **TMDB** on each request. What _is_ stored locally is a thin spine (`titles`, keyed by `(kind, tmdb_id)` for films and series) plus **synced, authoritative metric data** (Bechdel rating, UM advisory flags) and a **spine-independent UM catalogue** (`um_source`) that powers the runtime disambiguation picker. DDD data is fetched live and streamed, not persisted.

Each metric is designed to show **two scores side by side**: the original authoritative source (Bechdel, UM, DDD) and a **MIDB community rating** contributed by users who have watched the film. Movies will also have a **comments section** for viewer context and discussion. Community ratings and comments are the next major feature milestone: the per-metric community tables and `comments` exist (remediation PR 4), and the `/user/*` area already has the profile editor and the (empty) rating and comment history views.

## High-level data flow

```
                  ┌────────────────────────────────────────────┐
   Browser  ──►   │  SvelteKit server (hooks + load functions)  │
                  └──────┬──────────────┬──────────────┬────────┘
                         │ (via #lib/server/cache: Cache API  │
                         │  + per-isolate memory)             │
            cached fetch┌─▼────────┐ ┌───▼──────┐ ┌─────▼───────┐
                        │  TMDB    │ │   DDD    │ │  D1 (SQLite)│
                        │  API v3  │ │   API    │ │  (Drizzle)  │
                        └──────────┘ └──────────┘ └─────────────┘
                         ▲            ▲ (streamed,   ▲
              poster / overview /     │  cached 1h)  │  synced source data:
              credits / imdb_id    trigger tags    titles + Bechdel + UM
              (cached 24h)

   Auth:  Browser ⇄ /api/auth/* (Better Auth handler, sessions in D1) ⇄ Google / Discord (SSO)
          hooks.server.ts reads the session lazily through `getAuth().api.getSession`
   Migrations: `wrangler d1 migrations apply` (`pnpm db:migrate:local` / `db:migrate:remote`)
               from `db/migrations`; the server never migrates on boot
```

- **Entry point** is the landing page at `/` (hero + search UX). The hero search is a **live, inline TMDB search**: typing queries a server proxy (`/api/search`, TMDB `search/multi`) and renders a results dropdown in place — there is no `/search` page. Results carry a `mediaType` (`movie`/`tv`) and route to the matching detail page.
- **Title identity** flows by **TMDB id** through the URL (`/movie/[movieId]`, `/tv/[seriesId]`), but the internal join key across metric sources is **`imdb_id`** (the Bechdel/DDD key). On a detail-page load the live TMDB title is resolved to a local `titles` row via **read-only** `getTitleRow(kind, ref)` (matching on `(kind, tmdb_id)` then `imdb_id`); a GET never mutates the DB. Movies and series share the TMDB numeric id space, so `kind` is part of the key; there are no synthetic ids.
- **Metric data** comes from three places: **Bechdel + UM** are stored in D1 and rendered server-side (SSR); **DDD** is fetched live from its API and **streamed** so a slow external call never blocks first paint. (Bechdel is movie-only; series surface UM + DDD.)
- **Caching.** TMDB title fetches (`getMovie`/`getSeries`), TMDB search (`searchTitles`) and DDD lookups go through `#lib/server/cache` so repeat visits to a title skip the external round-trip — the dominant source of detail-page latency. The backend is the Cache API behind a per-isolate memory level (see _Server cache_). Public page loads set `PUBLIC_PAGE` (the landing, whose films are random per request, sets `PUBLIC_NO_STORE`), `/api/search` sets `PUBLIC_SEARCH` and `/img/tmdb/*` sets `PUBLIC_IMAGE`, so Workers Caching serves repeat requests without running the Worker (see _Caching policy_).
- **Auth** is Better Auth, mounted at `/api/auth/*`; the hook gates `/user/*` on the session cookie, and server-rendered public pages never depend on the user (see _Auth flow_).

**Key structural choices:**

- The database layer (`db/`) sits _outside_ `src/`, exposed to app code as `#db/*` (package.json `imports`). App code imports `db` from `#lib/server/db.ts` (a lazy proxy over the `DB` binding); scripts call `openScriptDb()` from `db/scripts/lib/db.ts`. Both build it with `createDb` from `db/client.ts`, which reads no env itself.
- **Shared server logic does not live inside route folders.** Anything two routes both need (DB queries, external API clients) lives under `#lib/server/`; route folders keep only their route files (`+page.svelte` / `+page.server.ts` / `+server.ts`).

### File-organisation conventions

- **`#lib/server/**` is the server-only boundary.** SvelteKit fails the build if any client-reachable code imports from it. Secrets (`TMDB_API_TOKEN`, `DDD_API_KEY`, …) come from `#lib/server/env.ts`and DB access lives here only.`data/`= D1;`integrations/` = external HTTP clients.
- **Components for types, never routes.** A component that needs a `Movie`/`Series`/`TriggerTag` type imports it from `#lib/media/types/*` — `media/types/ddd.ts` re-exports DDD types from `integrations/ddd-types.ts` (not `ddd.ts`) as **types only** (erased at build, so no server runtime leaks into the client bundle). Components no longer reach back into `routes/.../`.
- **`ui/` vs domain.** Title-specific UI lives in domain folders (`movies/*`, `landing/`, `search/*`, …). `ui/` holds generic primitives with at least two real consumers: today `ui/badge.svelte` and `ui/notice.svelte`.
- **Imports use `#lib` and `#db`**, the subpath imports in package.json (`#lib/*` → `src/lib/*`, `#db/*` → `db/*`), with explicit extensions (`#lib/media/utils/format.ts`, `#lib/components/ui/badge.svelte`); relative `./` is reserved for same-folder siblings. The Node-run scripts under `db/` and `scripts/` (and what they import: `db/client.ts`, `db/schema/*`, `db/lib/*`) use relative `.ts` imports, so they stay free of the app's imports map, and `erasableSyntaxOnly` keeps their syntax strippable.
- **Tests are co-located in a `__tests__/` subfolder** at each location (the `unit` project globs `src/**/*.{spec,test}.{js,ts}` and `db/**/*.spec.ts` at any depth). Specs that touch the database are named `*.db.spec.ts` and run only in the `db` project (`pnpm test:db`); the `unit` project excludes them and mocks `#lib/server/db`. Playwright e2e specs live in top-level `e2e-tests/`.

## Styling & theming

The styling system is **Tailwind CSS v4, CSS-first**. There is no JS theme config in the build path — the source of truth is `src/app.css`.

- **Entry & tokens.** `app.css` begins with `@import "tailwindcss"`. Build-time design tokens are declared in a `@theme { … }` block. Semantic _colors_ are exposed through **`@theme inline { --color-*: var(--*) }`** so utilities re-resolve at render time and a theme switch re-cascades without rebuilding.
- **Design-token system.** One definition per token with `light-dark()`: `--surface`, `--surface-raised`, `--surface-sunken`, `--ink`, `--ink-muted`, `--border`, `--border-strong`, `--brand` / `--brand-strong` (the project violet: the main action, links, focus, active states, the women data series), `--on-brand` / `--on-ink` (text on filled violet or ink), `--brand-wash` (8% lilac plate), `--src-bechdel` / `--src-um` / `--src-ddd` / `--src-tmdb` (four violet shades, one per source), `--accent` (suffragette green), the gender series `--seg-*`, status `--success` / `--warn` / `--danger` / `--info` with `-soft` fills (`--success` is `--brand`, so a good value stays violet; caution is copper, harm a darker raspberry, apart in lightness as well as hue so colour-blind readers can tell them apart), `--secondary-soft`, and elevation `--shadow-subtle` / `--shadow-md` / `--shadow-float` / `--shadow-brand`. Every solid status token passes 4.5:1 on its soft fill and on `--surface` in both themes. Type: `--font-display` **Inter Tight** (Google Fonts, 600/700, loaded in `app.html`) and `--font-body` / `--font-mono`, the system UI and mono stacks; `body` is tracked `-0.02em`. Shared classes in `app.css`: `.display` (Inter Tight 700), `.label`, `.link`, `.num`, `.card` (hairline 12px container), `.btn` + `--brand` / `--ink` / `--ghost` / `--pill`, `.disk` (icon disk: `--hue`, `--disk`), `.highlight` (coloured text over a highlighter stroke; its colour comes from a `.tone-*` class: `pos` / `mid` / `neg` / `neutral` mirror the badge tones, `bechdel` / `um` / `ddd` / `tmdb` the source shades), `.chip` (30px hairline pill for secondary links and the hero pager). Base layer themes focus rings, selection, caret, scrollbars, and `select`. The look follows a pinned reference (Podscan.fm) on MIDB's palette: see `DESIGN.md`.
- **Theme switching.** `:root { color-scheme: light dark }` makes `light-dark()` follow the system; `:root[data-theme='light'|'dark']` pins `color-scheme` (manual override via the theme toggle, written to `document.documentElement.dataset.theme`).
- **Fonts.** Inter Tight is self-hosted: `@font-face` rules in `app.css` for the 600 and 700 woff2 files in the latin, latin-ext and vietnamese subsets (each with the package's `unicode-range`, so a subset downloads only for titles that use its letters; `font-display: swap`), the files in `static/fonts/`, and a `<link rel="preload">` for each latin file in `app.html` (only those: the landing's 600 sentence would otherwise shift layout when its file arrives). No request leaves for Google Fonts.
- **Mobile chrome tint.** A `<meta name="theme-color">` in `app.html` tints the mobile browser chrome with `--surface` (`#fbfafc` light / `#141217` dark). The pre-paint script in `app.html` resolves the active theme (manual override → system preference) before first paint; `themeToggle.apply()` re-sets it on switches. The hex values are duplicated in both places: keep them in sync with `--surface` in `app.css`.
- **No `tailwind.config.js` and no PostCSS config.** Tailwind v4 reads everything from `app.css`.
- **Svelte `<style>` blocks** use `<style lang="postcss">` with `@reference "…/app.css"` so `@apply` resolves v4 tokens. `vitePreprocess({ style: false })` prevents vitePreprocess from running its own PostCSS pass.

## Copy & voice

User-facing copy follows a small house style. Apply it when writing or editing any visible text (page content, taglines, labels, notes); it does not govern code comments, `<title>` tags, or commit messages.

- **Matter-of-fact register.** State what a thing is and what happens, plainly. No marketing/salesperson tone, no rhetorical questions ("Want the short version first?"), no reader flattery or persuasion ("the only interest it serves is yours"), no hedging filler ("just", "the gist", "roughly where it stands"). The `/resources` page is the reference for the target voice: declarative, concrete, sourced.
- **Third person everywhere.** Address the reader in the third person ("the page lists the possible matches", "a reader"), not the second ("you can pick"). The landing page follows the same rule since the copy pass: its old motto ("Know before you watch") was replaced by a plain statement of what the site covers.
- **Essentials only.** Each fact once, in the fewest words that keep it. No taglines, no intros restating headings, no template subheadings, no stock phrasing ("at a glance", "distilling", "so you decide"). `/resources` was rewritten to this standard: one short lede, then plain paragraphs per source, with subheadings only for the two verdict axes.
- **Terminology.** film / series (not movie / TV), verdict, warning (DDD), flag and concern (UM), source, Bechdel Test. Sentence-case labels.
- **No em dashes (—) in copy.** Restructure instead: split into separate sentences, or use a colon when a list/expansion follows. En dashes (–) are correct in number and relationship ranges (`0–3`, `adult–teen`) and stay.
- **Claims must be code-backed.** Anything asserted to the user (privacy properties, how a metric is computed, thresholds) must match the code. The verdict-card explainer mirrors `verdict.ts` (exact flag tiers and scoring thresholds); the landing privacy line was verified against the codebase (no trackers, analytics or ads). The copy pass removed two claims the code did not back: "ratings submitted by the MIDB community" (no rating UI exists yet) and DDD warnings being "sorted by margin of the vote and grouped by category" (the client does neither). When the code changes, update the copy.

## User & roles

Users are Better Auth users: `user.id` is Better Auth's opaque id (text). `hooks.server.ts` exposes `locals.getUser()`, which reads the session through `getAuth().api.getSession` and then the `user` row by id, only when a route asks for it (memoised per request). The row is read fresh so a ban, a role change or a deleted account applies on the next request, although the session cookie cache lets the session itself read as valid for five minutes. A banned user (`banned_at` set) resolves to `null`. Public pages never call it.

**Client shape:** the only user object that reaches the browser is `PublicUser` (`#lib/media/types/user.ts`: `id`, `username`, `avatarKey`, `role`, `displayName`), built by `toPublicUser` in `user-queries.ts`. `id` is the opaque Better Auth id, which lets the client recognise its own comments in lists that are the same for everyone. `displayName` is the username (`"Account"` only for a row with none); it reaches only the account holder's own responses (`/api/me`, the `/user` layout). The real email reaches the client on `/user/profile` and in the account holder's own `/api/auth/*` responses, which are `private, no-store` (Better Auth returns the user row, so a passkey-only account's placeholder is in them too, and no page shows it). Loads never return a `UserRow`.

**Placeholder email.** A passkey-only account has no email, and Better Auth needs a unique one, so it gets `<id>@users.invalid` with `email_verified` false (`placeholder-email.ts`). `realEmail(user)` is null for it, and neither `toPublicUser` nor `/user/profile` shows it. When a Google or Discord account is linked, `adoptProviderEmail` (an `account.create.after` hook) replaces the placeholder with the provider's verified email, unless another user already has that address.

**Role enum (`user_role`):** `user` | `moderator` | `administrator`. Default `user`. Authorization always reads the DB role through `requireRole` (`#lib/server/auth/guards.ts`); Better Auth has no concept of MIDB roles. Promote via `pnpm db:seed:admin <email>`.

**Profile fields:** `username` (text, CHECK length at most 32, case-insensitive unique via `lower(username)` index, validated `^[a-z0-9_]{3,32}$` + reserved-name blocklist), `avatar_key` (text, CHECK length at most 48, validated against avatar registry). `role`, `username` and `avatar_key` are `additionalFields` with `input: false`, so no Better Auth endpoint writes them.

**Moderation state.** `banned_at` and `ban_reason` are set by `banUser`, which also deletes the user's sessions in one `db.batch()`. The `session.create` hook refuses a new session for a banned user (`APIError` FORBIDDEN). `muted_until` is read by the comment write paths (`authorizeWrite`); every write path reads ban and mute state from the DB, never from the session cookie.

- The flags are read through the join (`getUmEntry`), so a UM sync is reflected immediately and there is one row shape (`UmEntry`). Matched by `clean_title` at sync time using a year-aware policy (see Source sync). User choices are never persisted (see UM Disambiguation below).

**`source_sync`** (`sources.ts`) — one row per synced source: `source` text PK (CHECK), `last_success_at` timestamp, `rows_changed` integer. Written by each sync on success (`stampSync`) and read by `getSourceSyncDates`. `bechdel` is the last Bechdel run of any kind and `bechdel_sweep` the last full sweep; the values are the `syncSource` tuple in `sources.ts`.

**Auth tables** (`auth.ts`) — Better Auth's `user`, `session`, `account`, `verification` and `passkey`, generated with the `auth` CLI and merged by hand; `create-auth.ts` maps them by model name. `user`: `id` text PK, `name`, `email` (unique, not null), `email_verified`, `image`, `role` text `user`|`moderator`|`administrator` default `user` (CHECK), `username` text(32) nullable, `avatar_key` text(48) nullable, `banned_at`, `ban_reason` text(500), `muted_until`, `timestamps()`. Unique index on `lower(username)` (case-insensitive, NULLs don't collide); index on `role`. `session`, `account` and `passkey` reference `user` with `ON DELETE CASCADE`. `passkey` stores the credential's public key, never a private one.

**Community tables** (`community.ts`) — one table per metric shape so each can hold what it names. The Bechdel, UM and DDD tables are empty and have no write path (see Known gaps); `community_content_reports` and `title_count_flags` are the live reader-report tables.

- **`community_bechdel_ratings`**: `user_id` → `user.id` (cascade), `title_id` → `titles.id` (cascade), `rating` integer (**CHECK 0..3**, `cbr_rating_range`), `timestamps()`. PK `(user_id, title_id)` (resubmit = upsert), index `cbr_title_idx (title_id)`.
- **`community_um_reports`**: `user_id`, `title_id` (both cascade), the 9 flag columns as explicit booleans (`umFlagColumns()`, same shape as `um_source`, aggregatable as `avg(col)`), `timestamps()`. PK `(user_id, title_id)`, index `cur_title_idx (title_id)`.
- **`community_ddd_votes`**: `id` text PK, `user_id`, `title_id` (both cascade), `topic_id` integer, `season`/`episode` integer nullable (NULL = whole title), `yes` boolean, `timestamps()`. Unique index `cdv_vote_uniq` on `(user_id, title_id, topic_id, season-or--1, episode-or--1)`, so a NULL season or episode counts as equal to another NULL (the expression is a `CASE`, because drizzle-kit splits an expression on commas, so `coalesce(x, -1)` is not emitted correctly), index `cdv_title_topic_idx (title_id, topic_id)`.

- **`comments`**: `id` text PK, `title_id` → `titles.id` (cascade), `user_id` → `user.id` (cascade), `parent_id` and `root_id` (self-FKs, cascade; null on a root), `body` text (**CHECK `length(body)` from 1 to `COMMENT_BODY_MAX`**), `status` text `pending`|`published`|`hidden`|`rejected`|`deleted` (default `pending`, CHECK), `score` and `reply_count` integers (default 0), `edited_at`, `moderation_source` `ai`|`blocklist`|`moderator`|`reports` (nullable, CHECK), `moderation_reason` (CHECK ≤ `MODERATION_REASON_MAX`), `ai_verdict` (JSON text, CHECK `json_valid`), `timestamps()`. Indexes `(title_id, status, created_at)` and `(title_id, status, score)` for the two list sorts, `(root_id, created_at)` for a thread, `(user_id, created_at)` for history. The enum tuples and the limits live in `db/lib/comments.ts` (re-exported by `#lib/media/utils/comments.ts`), which the schema imports.
- **`comment_votes`**: `comment_id` (cascade), `user_id` (cascade), `value` (**CHECK ±1**), `timestamps()`. PK `(comment_id, user_id)`.
- **`comment_reports`**: `id` text PK, `comment_id` and `reporter_id` (cascade), `reason` (`hate`|`harassment`|`spam`|`sexual-content`|`threat`|`other`), `note` (CHECK ≤ `REPORT_NOTE_MAX`), `status` `open`|`resolved`|`dismissed`, `resolved_by` (set null), `timestamps()`. ### Migrations

One SQLite baseline, `db/migrations/0000_init.sql` with its snapshot and journal, generated by drizzle-kit (`pnpm db:generate`, `dialect: 'sqlite'`, `drizzle.config.ts`). While the schema is still changing the baseline is regenerated (delete `db/migrations`, then generate) instead of stacked; once a database holds data, a change is a new migration, fixed forward and never rolled back by hand. Commit the generated SQL, snapshot and journal in the same change as the schema change; never hand-write or hand-edit a snapshot JSON. CI's `migrations` job runs `drizzle-kit generate --name drift_check` and fails if `db/migrations` changes. `db:generate` prompts (rename vs create) need a TTY; without one, run it as `script -qec "pnpm exec drizzle-kit generate" /dev/null` and answer the prompts.

Wrangler applies the files (`wrangler d1 migrations apply`, `migrations_dir` in `wrangler.jsonc`): `pnpm db:migrate:local` for the local database in `.wrangler/state` and `pnpm db:migrate:remote` for the deployed one. Each file is applied atomically and a failure stops the run. Foreign keys stay on (`.claude/rules/code-standards.md`, Database, says what a table rebuild sets). **Boot does not migrate.** The `drizzle.config.ts` D1 HTTP credentials (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID`, `CLOUDFLARE_API_TOKEN`) are read only when all three are set.

## Source sync

The Bechdel Test, Unconsenting Media (UM) and TMDB popularity are read from the sources' public files by the scripts in `db/scripts/sync/`; nothing from them is committed to the repository. The parsers are pure functions in `db/lib/sources/` (`parseUmFeed`, `parseBechdelYearPage`, `readBechdelYear`, `parseBechdelRss`, `readTmdbExport`) with every selector in one place, unit-tested against trimmed real responses in `db/test/fixtures/`. Each sync exports its core as a function taking `(db, source, options)`; the Node entry point (`if (isMain(import.meta.url))`) goes through `runSync` (`db/scripts/sync/lib/run.ts`, flags in `args.ts`), which opens the database with `openScriptDb(parseTarget(argv))` from `db/scripts/lib/db.ts`, closes it, and turns a failure into a non-zero exit. The database is the local D1 by default (wrangler's `getPlatformProxy`, in `.wrangler/state`), or with `--remote` the deployed one through `drizzle-orm/sqlite-proxy` over D1's REST `raw` endpoint (`db/scripts/lib/remote-d1.ts`, tested with a mocked `fetch`; not run against a live account). `--fixtures` swaps the live sources for the fixtures (`fixtureSources()` in `db/scripts/sync/lib/sources.ts`), so a run works offline; it always sweeps.

Every request carries the `MIDB-sync` User-Agent, a timeout and one retry (`fetchSource`). A sync reads and validates everything before its first write, and a source with no rows (or a changed shape) throws, so a fetch or parse failure changes nothing and does not stamp `source_sync`. `syncUm` also refuses, before any write, a feed that leaves films or series empty or would delete more than `MAX_DELETED_SHARE` of the stored rows. A database error part way through a run leaves the batches before it applied, and the next run finishes the diff. Writes are diffs: a run writes only rows that differ, so an unchanged source writes nothing. Each bulk write is split with `chunkForD1` to stay under D1's bound-parameter limit and grouped with `db.batch` (`runBatches`). A successful run stamps its source in `source_sync` with the time and the rows changed.

1. **`db:sync:um`** (`sync-um.ts`) — fetch `https://www.unconsentingmedia.org/list.json` (no keys).
   - `parseUmFeed` keeps the items whose `itemType` is `movie` or `TV show`, validates them with zod, and maps the nine flags. It derives a `(titleKey, umYear)` pair per item using **`stripTrailingYear`** (UM's `cleanNameArticles` often embeds the year: `"wuthering heights 2026"`); UM's `yearOfRelease = 0` becomes NULL. `source_updated_at` is the feed's `updatedAt`.
   - Upserts `um_source` rows that are new, whose `updatedAt` is newer than the stored one, or whose derived columns (`clean_name`, `clean_title_key`, `year`) differ from the stored ones, so a matcher fix reaches stored keys. The nine flag keys come from `umFlagColumns()` for the parser's zod shape, its mapping and the upsert. Deletes rows missing from the feed, removing their `title_um` bindings first (`um_id` has no cascade).
   - Recomputes the bindings for every UM film against the film `titles` and writes the difference, so a new or renamed item, or a film the Bechdel sync added, is bound on the next run. `matchUmFilm` applies the **year-aware policy**: (1) only one film with the key → bind (unambiguous); (2) several → bind the exact `(titleKey, umYear)` hit; (3) several, no year hit → unmatched (`ambiguous`). One UM film per title: the highest `um_id` wins. Only `(title_id, um_id)` is written to `title_um`. TV rows are never bound here; the runtime picker covers them.
   - Prints the counts and the unmatched films (capped at `UNMATCHED_LINES_SHOWN` lines) to the job log. It does **not** create `titles` rows from UM data.
2. **`db:sync:bechdel`** (`sync-bechdel.ts`) — the JSON API is gone (410), so the data comes from the `https://bechdeltest.com/year/<YYYY>/` pages and the feed of the last 50 additions, at the pace `BECHDEL_INTERVAL_MS` sets (`db/scripts/sync/lib/sources.ts`).
   - The daily run reads the feed's years plus the last `RECENT_YEARS` years (`sync-bechdel.ts`). `--full`, and a database with no `bechdel_sweep` stamp, sweep every year from `BECHDEL_FIRST_YEAR` (`bechdel-html.ts`). Year pages are paginated, so `readBechdelYear` follows the pager (`/year/<YYYY>/page/<n>/`); a year with no films has no page (404) and counts as empty, and a year whose pages do not add up to the film count the site declares throws.
   - Upserts `titles` (`kind: 'movie'`, keyed by `imdb_id`; title, `clean_title`, year) and `title_bechdel` (`bechdel_id`, rating). A film the site lists without an IMDb id (`ttNone`) is skipped and logged. Nothing is deleted. A full sweep also stamps `bechdel_sweep`; the Bechdel section's "Updated" date uses that stamp, because daily runs reread only the recent years.
3. **`db:backfill:tmdb`** (`backfillTmdb.ts`) — resolve null `tmdb_id` on **movie** titles with an IMDb id via TMDB `/find/{imdb_id}` (`resolveTmdbId`, through `fetchSource`; only an OK answer without a film counts as not found, any other failure throws). Needs `TMDB_API_TOKEN`. `getOrCreateTitleRow` will also backfill once a write endpoint uses it.
4. **`db:sync:popularity`** (`sync-popularity.ts`) — stream TMDB's daily `movie_ids_*` and `tv_series_ids_*` exports (gzipped NDJSON, no auth, ready by 08:00 UTC; the day before is used when today's is not out) and update `titles.popularity` and `popularity_at` for titles that have a `tmdb_id`, when the score changed. The exports are read, not stored.

**Schedule.** `.github/workflows/sync-sources.yml` runs `db:sync:all --remote` once a day, with `--full` on Sundays. The README (Daily source sync) owns the time, the repository secrets and the 60-day rule. The job runs only on the canonical repository, has `contents: read`, no pull-request trigger and no persisted checkout credentials, and gives the secrets to the one step that uses them. Title pages show each sync's date (Detail pages, `syncedAt`).

**`db:sync:all`** runs 1, 2, 3, 4 in order and fetches the UM feed once. The two TMDB steps are skipped with a notice when `TMDB_API_TOKEN` is unset, so the other two need no account; with `--fixtures` the backfill is skipped (it calls TMDB's API) and popularity reads the fixture exports. The UM bindings need the film `titles`, so when the Bechdel sync adds films, `db:sync:all` runs the UM sync a second time over the same feed to bind them. Re-running any step is safe.

**`db/lib/normalizeTitle.ts`** — two exports (the app imports it as `#db/lib/normalizeTitle`, the sync scripts relatively, so the matching key is one module):

- `normalizeTitle(title)` — lowercase, strip leading articles (en/fr/de/es/it), strip diacritics + punctuation, collapse whitespace. Must mirror UM's `cleanName` conventions.
- `stripTrailingYear(normalized)` — removes a trailing ` (19|20)\d\d` from an already-normalized string, returns `{ key, year }`. Used to handle the ~12% of UM rows whose `cleanNameArticles` embeds the year.

Both are covered by unit specs (`db/lib/__tests__/normalizeTitle.spec.ts`). `db/scripts/__tests__/sync.db.spec.ts` covers the sync against the fixtures: the upsert-only diff (a second run writes nothing), deletions removing bindings first, the Bechdel upserts, the popularity update, `source_sync` stamping, and a source with no rows failing with nothing deleted.

## Detail pages (`src/routes/movie/[movieId]/`, `src/routes/tv/[seriesId]/`)

The flagship pages. Server-rendered for DB metrics, **streamed** for the live DDD call. Movies and series share one loader (`loadTitle`) and one client page-state class (`TitleView`); they differ only in which TMDB call runs and which metrics apply.

**Server (`+page.server.ts`, both pages):**

```ts
setHeaders({ ...PUBLIC_PAGE }); // #lib/server/http/cache — edge-cacheable, so never read the user here
return loadTitle('movie', params.movieId); // or loadTitle('tv', params.seriesId)
```

**`#lib/server/titles/load-title.ts`** — `loadTitle(kind, tmdbId)` (overloaded, so the movie page gets `media: Movie` and the TV page `media: Series`):

1. `getMovie` / `getSeries` (TMDB, cached via `#lib/server/cache/index.ts`, TTL in `integrations/tmdb/client.ts`);
2. `getTitleRow(kind, media)` — read-only; `null` if the title was never seeded (GET routes never call `getOrCreateTitleRow`);
3. with a row: `getBechdel` (movie only, `null` for series) and `getUmEntry` in parallel; without one, both `null` and no DB round-trip;
4. no seeded UM binding → `getUnconsentingCandidates(media)`;
5. `getTriggerTagsLive(media.imdbId)` (movie) or `getTriggerTagsForSeries(media)` (tv), returned **un-awaited** so it streams.

Page data on both pages: `{ media, bechdel, umEntry, umCandidates, syncedAt, triggerTags }`. `syncedAt` is `getSourceSyncDates()` (`#lib/server/data/source-sync.ts`): ISO times of each source's last successful sync, read from `source_sync` and cached with `getCached` (TTL in that file, under the pages' edge TTL). It is read in parallel with the source rows, never from the request's user. The Bechdel section passes the `bechdel_sweep` time and the UM section the `um` time to `collapsibleSection` as `updatedAt`, which renders "Updated <date>" after the "Source:" link (`formatDate`, UTC, so server and client agree). It is part of the server-rendered page, so nothing shifts; a source with no row, or a section with no source link, shows no label. DDD and TMDB are live and have none.

**DDD live client (`#lib/server/integrations/ddd.ts`):** `getTriggerTagsLive(imdbId)` (movies, imdb lookup) and `getTriggerTagsForSeries(series)` (title text-search + tmdb/year match). Two-step fetch with `X-API-KEY`; results cached via `#lib/server/cache` (TTLs in `ddd.ts`; keys `ddd:imdb:…` for movies, `ddd:tmdb:…` for series); a non-OK DDD status, from the search or the media request, is cached for a shorter TTL instead (the TTL is a function of the lookup), so an outage neither hides a title's warnings for long nor sends a request per visit. Returns `TriggerTag[]` filtered to `yesSum >= noSum && yesSum > 0`, carrying season/episode scoping for series. Unit tests reset it with `clearCache()` from `#lib/server/cache`. Public types (`TriggerTag`, `DddResult`) live in `ddd-types.ts` — `ddd.ts` re-exports them; `media/types/ddd.ts` imports from `ddd-types` directly so type consumers never transitively load the client.

**Client page state (`#lib/media/utils/titleView.svelte.ts`):** `new TitleView(() => data, kind)` in the page script. All `$derived` over the load data:

Both `+page.svelte` files keep only markup and their own sections: the Bechdel criteria ladder (and its `.criterion-*` styles) on movies, the `DddEpisodeSelector` snippet on TV.

**`#lib/server/data/title-queries.ts`** — identity resolution:

- `getTitleRow(kind, ref)` — **read-only**. Tries `(kind, tmdb_id)` → `(kind, imdb_id)`; returns the row or `null`. Used on GET routes so page visits never mutate the DB.
- `getOrCreateTitleRow(kind, ref)` — **write path**. Same lookup, then a race-safe insert on a miss (`ON CONFLICT DO NOTHING RETURNING`, then read again), then a backfill of whichever id was null (skipped if another row owns it). Reserved for write endpoints (community ratings, the first comment on a title) that need a guaranteed `titles.id` FK target; no GET route calls it.
- `TitleRef` is the structural `{ title, imdbId, tmdbId, releaseDate }` that both `Movie` and `Series` satisfy. Unknown release dates give a NULL year.

**`#lib/server/data/catalogue.ts`** — landing page data (seeded tables only, read-only, tested in `catalogue.db.spec.ts`):

- `getCatalogueCounts()` — row counts of `title_bechdel` and `um_source` for the Bechdel and Unconsenting Media source cards on the landing; cached (`catalogue:counts`, TTL in `catalogue.ts`).
- `getPopularRatedFilms(limit, { requireUmEntry, requireTmdbId })` — movies with a Bechdel rating ordered by `titles.popularity` (TMDB's score, NULLs last), with the bound UM entry's concern count and its UM-only safety tier (`scoreSafety(entry, empty DDD)`). `requireUmEntry` inner-joins the UM binding so only films with an entry come back; `requireTmdbId` drops films without a TMDB id.
- `getRandomRatedFilms(count, pool)` — `count` films sampled at random (partial Fisher–Yates) from the `pool` (default 100) most popular films with a UM entry and a TMDB id; returns `LinkedRatedFilm` (`tmdbId: number`). The landing hero calls it per request; the ranked pool is cached (`catalogue:hero-pool:v2:<pool>`, TTL in `catalogue.ts`) and the sampling runs on every call, so the films stay random while the query runs once per TTL per isolate or data centre.

**`#lib/server/data/sources.ts`** — seeded metric reads:

- `getBechdel(titleId)` — `title_bechdel` row or `null`.
- `getUmEntry(titleId)` — joins `title_um` → `um_source`, returns `UmEntry | null`.
- `toUmEntry(row)` — the single `um_source` → `UmEntry` mapper, also used by `um-candidates.ts`.

**`#lib/server/data/um-candidates.ts`** — UM disambiguation algorithm:

- `getUnconsentingCandidates(ref)` — queries `um_source` by `cleanTitleKey` (plus the singular/plural alternate); applies year-aware filtering (see UM Disambiguation); returns full `UmEntry`s so a picked candidate renders identically to a seeded binding.

## Comments (`src/lib/server/data/comment-*.ts`, `src/routes/api/…/comments`)

- **Threading.** A root has no `parent_id`. A reply stores the comment it answers as `parent_id` and its thread's root as `root_id`, so a reply to a reply stays in the root's thread and the list can say whom it answers (`CommentView.inReplyTo`). The list renders a root plus one level.
- **Statuses.** `pending` (awaiting a decision), `published` (public), `hidden` (a moderator took it out of view), `rejected` (the author sees the reason), `deleted` (the author's soft delete). Only `published` is in the public list. A comment that is not published but has published replies stays in its thread as a placeholder: `removed`, no body, no author. The author sees their own pending and rejected comments through the viewer endpoint.
- **Moderation.** `decideStatus` (`#lib/server/moderation/decide.ts`) is the one place that decides what status a new or edited comment starts in; creating and editing are the only callers, so nothing else costs a model call. It runs in order:
  1. **Blocklist** (`blocklist.ts`). Whole-word match on text folded for case, accents, leetspeak, repeated letters, separators and spaced-out letters, against the public `BLOCKLIST_TERMS` plus the private `MODERATION_EXTRA_TERMS` (comma or newline separated, read per call). A hit is `rejected` with source `blocklist` and no API call; its reason names the term when it is a public one, and a private term keeps the general reason.
  2. **Classifier** (`classify.ts`, client from `integrations/anthropic.ts`). With no `ANTHROPIC_API_KEY` it reports `ai-unavailable` and the comment is `pending`, unless `MODERATION_DEV_AUTO_APPROVE=1` and `PUBLIC_ORIGIN` is a localhost origin, which publishes it with no source. Otherwise one `messages.create` call runs under one overall deadline (`MODERATION_DEADLINE_MS`; the per-attempt timeout and the one retry in `integrations/anthropic.ts` sit inside it) and its text is read in two steps: the SDK's parse over `ModelVerdict`, which carries no bound so a long reason cannot discard the answer, then the strict `Verdict` (severity 0 to 3, known categories). The reason is cut to `MODERATION_REASON_MAX`, and an empty one on a `reject` becomes `FALLBACK_REASON`. The model is `MODERATION_MODEL` (`wrangler.jsonc`), else `DEFAULT_MODEL` in `classify.ts`. The system prompt is frozen and public; the title, the parent comment and the comment arrive as tagged data (`<` is escaped), and nothing about the author is sent. A `refusal` or `max_tokens` stop (read before the text), text that fails either parse, the deadline or a per-attempt timeout, a rate limit or any other error is a failure with a code (`ai-*`). An edit sends the parent's text only while the parent is `published`.
  3. **Policy** (`policy.ts`, pure). Blocklist hit: `rejected`. `allow`: `published`. `review` or a failure: `pending`. `reject` at `REJECT_MIN_SEVERITY` or more: `rejected` with the verdict's reason; below it: `pending`.

  The stored `ai_verdict` is the verdict JSON plus the model id, or `{ "failure": code }` for a failed check; `/user/moderation` reads its categories. The copy on `/resources` (Comments and moderation) mirrors `policy.ts` and changes with it.

- **Counts.** `reply_count` counts published replies, to the comment (as `parent_id`) and, on a root, in its whole thread. Every status change goes through `statusMove` (`comment-status.ts`), which adjusts the parent's and the root's count in the same `db.batch` and guards both statements on the comment still being in the status it was read in, so a lost race changes nothing. `score` is recomputed from `comment_votes` in the same batch as each vote, so repeating, flipping or removing a vote cannot leave it off.
- **Atomic writes.** Every multi-row write is one `db.batch` (D1 has no transactions; a batch is one): a vote and its score, a reply and its counts, a moderator action and its `moderation_actions` row, a third open report and the move to `pending` (source `reports`, at `REPORT_THRESHOLD`).
- **Title rows.** The first comment on a title resolves its row with `getOrCreateTitleRow` after fetching the title from TMDB (`resolveCommentTitle`); every GET uses `getTitleRow` and answers an empty list for a title with no row.
- **Endpoints** are listed under Routes. Every write runs `requireUser` (a banned account is signed out by the hook, so it gets 401), the mute check on the fresh user row (403), `rateLimit` with the user id, then zod validation (`authorizeWrite`, `readBody` in `#lib/server/http/comment-request.ts`). The list is `PUBLIC_COMMENTS` with a `Cache-Tag` (see Caching policy). Comment writes, edits, deletes and a report that reaches the threshold purge the tag with `purgeTitleComments`; votes do not. Moderator actions return the affected title so the caller can purge it the same way (`/user/moderation`'s form actions do).
- **UI** (`src/lib/components/comments/`, `moderation/`). `commentsSection` ends the `.sections` of both title pages, inside `{#key tmdbId}`; it is a `CollapsibleSection` with no icon disk, and the page stays edge-cached and cookie-blind because everything personal loads in the browser.
  - **State.** `CommentsState` (`commentsState.svelte.ts`) holds the list (sort, cursor), the viewer state and every write; requests go through `requestJson` and failures through `describeFailure` (`commentApi.ts`), stored per control (`compose`, `reply:<id>`, `edit:<id>`, `delete:<id>`, `vote:<id>`, `report:<id>`, `load`, `more`, `viewer`) so the component shows each beside its action. A write patches the state from its response, because the list is edge-cached and the purge lands after the write.
  - **Loading.** The list fetch starts on mount into a `.slot` with a reserved height and `aria-busy`. A reader who is probably signed in (the `midb_hint` cookie) also starts the viewer fetch at once, and the list waits for it, so their own comments never push the list down. `buildThreads` (`commentThread.ts`) merges the viewer's pending and rejected comments into the public threads; an own comment that is also in the list as a placeholder (an edited comment with replies) replaces it in place.
  - **Rules shown.** No vote controls, report or reply-to-self on one's own comment; Edit and Delete on one's own in any status; removed comments with replies are placeholders; a reply to a reply says "In reply to name"; a delete confirm names what is lost. A muted account sees the mute and its end in place of the composer (the viewer endpoint returns `mutedUntil`), with votes, replies, edits, deletes and reports disabled; the 403 sentence names a mute or a ban. `commentStatusTone` (`tones.ts`) maps a status to a badge tone.
  - **Shared pieces.** `commentAction` (quiet text action and square vote button), `commentConfirm` (a `.plate` with a message and two buttons), `commentComposer`, `commentReportForm`, `commentList`, `commentItem`; `/user/comments` reuses the composer, action and confirm in `commentHistoryRow`. `moderation/moderationItem` and `recentActionRow` are the moderation rows.
- **Moderation page.** The load reads the queues (`QUEUE_LIMIT` rows each) and `getSourceSyncDates`; `staleSyncSources` leaves out `bechdel_sweep` because the full sweep runs weekly. Every action goes through `act` in `+page.server.ts`: `requireRole`, `rateLimit` with `RL_MODERATE`, the query, then `purgeTitleComments` for a comment action. A refusal comes back as `fail` with a sentence for the row. A hide or reject can be undone from the log (`?/restore`); mute and ban have no undo.
- **Authority.** A moderator acts on ordinary accounts; only an administrator acts on a moderator; no one acts on an administrator or on themselves (`moderation-actions.ts`, `targetAllowed`, applied to a comment's author as well).

## UM Disambiguation

UM is the only source with no `imdb_id`, matched purely by normalized title. When a title has no seeded `title_um` binding, `getUnconsentingCandidates` resolves candidates from `um_source`:

| Title year known?          | Candidates                   | Outcome                                                                                                                     |
| -------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Yes                        | Exact year match found       | Return that one candidate → **rendered directly, no picker** (auto-match)                                                   |
| Yes                        | No candidate shares the year | Return the unknown-year (`year IS NULL`) entries, up to 5 (one → auto-match, several → picker); none → `[]` → **"No data"** |
| Unknown (no `releaseDate`) | Any                          | Return up to 5 candidates → **picker shown** (one → auto-match)                                                             |

**Nothing is persisted.** A user's pick lives only for the current page view — `TitleView.selectedUm` is a writable `$derived` keyed on `media.id`, so it resets on every title change. `TitleView` derives `umData = umEntry ?? autoUm ?? selectedUm`; the chip, section header, and flag list all read from `umData` so a picked candidate renders identically to a seeded binding.

**Why `um_source` exists:** `title_um` is a binding, keyed by `title_id`, so it only covers entries that _already matched_ a spine title. For ambiguous (same title, different year), TV, or spine-absent titles, `um_source` is the durable, re-queryable catalogue that doesn't require re-parsing the CSV per request. Bindings reference it, so both paths read one row shape.

**`UmEntry` type** (in `src/lib/media/utils/metrics.ts`, re-exported from `#lib/media/types/um.ts`) — `umId`, `cleanName`, `year`, `comment` + all 9 flag booleans. Seeded bindings and picked candidates both use it; the concern count is derived with `umFlagCount`, not stored.

**`umFlagCount(umData)` / `dddUrl(itemId)`** (in `src/lib/media/utils/metrics.ts`) — pure helpers shared by both detail pages and by the `umMetricSection` / `dddMetricSection` components. `umFlagCount` excludes `noRape` from the concern tally; `dddUrl` builds the deep-link or falls back to the DDD homepage.

## UM flag rendering

`UM_FLAGS` defines 9 flags. `noRape` is **inverted** — `true` means _no rape or sexual assault_ (a reassurance, not a concern). It is treated specially throughout:

- **Concern count** (`umFlagCount`, picker's `flagCount`) excludes `noRape`. The chip/status reads "0 concerns" when only `noRape` is true.
- **Flag list** — every flag is a row using the **shared circular marker** (see _Shared marker pattern_ below). `noRape === true` renders with `.um-flag--reassurance`: `ri-check-line` on `--success-soft`. All other present flags (`true`) → `.um-flag--present` with `ri-alert-line` on `--warn-soft`. Absent flags (`ri-subtract-line`) stay quiet (a transparent marker with a `--border` hairline) so present concerns lead the eye. The list is a column-gap-only grid (`minmax(17rem, 1fr)`, `gap: 0 --spacing-lg`). The UM note renders through `umComment.svelte`: notes over 360 characters (series notes run to thousands) clamp to four lines behind a "Show full notes" toggle.

## Shared marker pattern (metric row markers)

The metric sections in the detail page share **one visual language for per-item status rows**, so the stacked sections read as a family. Reuse it for any future metric checklist/ladder — don't invent a new marker shape.

- **Marker geometry.** A `1.375rem` round badge (`flex items-center justify-center rounded-full text-xs shrink-0`) holds a single Remixicon glyph or a step number. Rows are `flex items-center gap-sm`, `text-sm`, with `padding-block: var(--spacing-xs)` for the row rhythm.
- **States (tinted-fill convention).** _Active_ states fill the token's soft tint (`--warn-soft`, `--success-soft`, or `color-mix(in oklab, var(--brand) 14%, transparent)` for brand) with the solid token as glyph color. _Inactive_ states are a transparent marker with a `--border` hairline and an `--ink-muted` glyph. The active row's label goes `text-ink font-medium`; inactive stays `text-ink-muted`.
- **Token choice is semantic, not decorative.**
  - **Bechdel** (inline in the movie `+page.svelte`, `.criterion` / `.criterion-marker`) is a **cumulative ladder**: a met rung uses the **brand** tint + `ri-check-line`; an unmet rung stays quiet and shows `ri-close-line`. Brand, not a status tone: the overall `N/3` already reads from the section's status badge. No connector line.
  - **UM** (`umMetricSection`, `.um-flag` / `.flag-marker`) is an **independent flag set**, so no connector line. Present concerns are a real per-item signal → `--warn` tint; the inverted `noRape` reassurance → `--success` tint. Both correctly stay colored (the reassurance in `--success`, which is the brand violet).

## Live search (`src/lib/components/search/`)

- **`movieSearch.svelte.ts`** — `MovieSearchState` rune class: `query`, `results`, `activeIndex`, `loading`, `open`. Owns a `DebouncedQuery` (500 ms) over `/api/search`, the keyboard model (Arrow wrap-around, Enter→select, Escape→close), and navigation, which branches on `mediaType` (`resolve('/tv/[seriesId]', …)` vs `resolve('/movie/[movieId]', …)`). `search(q)` clears the previous rows and shows the spinner at once; a blank query closes the panel with no request. An error response (e.g. a 429) or a failed fetch ends in "no results". `connect()` watches navigation, and its teardown cancels a pending query. `optionId(id, mediaType)` builds the stable `aria-activedescendant` ids.
- **`DebouncedQuery`** (`#lib/media/utils/debouncedQuery.svelte.ts`, imported as `debouncedQuery.svelte.js`) — `push(query)` restarts the debounce window and aborts the in-flight `fetch` through its `AbortSignal`; a superseded response is dropped even if it resolves, so a stale result never overwrites a newer one. A blank query delivers the `empty` value at once, with no request; a rejected source also delivers `empty`. `cancel()` drops both. Nothing runs before the first `push`. Also used by the `/user/profile` username availability check (400 ms).
- **Query cap.** `SEARCH_QUERY_MAX_LENGTH = 120` (`#lib/media/utils/search.ts`): `searchInput` and `navbarSearch` set it as `maxlength`, and `/api/search` trims, then truncates anything longer (truncate, not reject).
- **`movieSearch.svelte`** — orchestrator: takes an optional `search` prop (a `MovieSearchState`) and otherwise instantiates one, wires `$effect(() => search.connect())`, click-outside dismiss, composes child components. Its listbox id comes from `$props.id()` (same on server and client). The landing page imports the component as `movieSearch.svelte`; the rune module is `movieSearch.svelte.js`. Mounted directly by the landing page.
- **Two independent consumers of `MovieSearchState`.** The landing page uses `movieSearch.svelte` with `searchInput`: a 12px-radius bar with a leading search icon, a spinner while loading, and a violet Search button. Submitting (the button, or Enter with no highlighted row) calls `MovieSearchState.submit()`, which opens the highlighted result or the first one. The global navbar uses `layout/navbarSearch.svelte`, a compact collapse-by-default field that reuses `MovieSearchState` + `searchResults`. Each consumer has its own `MovieSearchState`; the navbar one only mounts on non-landing routes (`pathname !== '/'`). Result rows show poster, title and "Film · 2015" / "Series · 2011"; the active row is a `--surface-sunken` fill.
- Panel visibility is `open && query.trim()` — `close()` flips `open` but preserves `query`/`results` so re-focus re-shows prior results without refetch.

## Server cache (`src/lib/server/cache/`)

A single cache fronts every external call so repeat detail-page visits skip the round-trip that dominates latency. It is not the page CDN: Workers Caching serves page responses (see _Caching policy_), and this store holds what the server fetches from TMDB and DDD and the landing's database queries.

- **API.** `getCached<T>(key, ttlMs, fetcher)` — returns the cached value or runs `fetcher`, stores it, and returns it. `ttlMs` may be a function of the fetched value, for a result that should live shorter (DDD's non-OK answers). A fetcher that throws stores nothing. Backend failures degrade to a cache miss (the fetcher still runs), so caching can never make a request fail — only slower. `clearCache()` (memory level and counters) is exposed for tests.
- **Backends** (`index.ts` picks one per call, because the dev server installs `caches` after the module loads):
  - **The Cache API** (`cache-api.ts`) where `globalThis.caches.default` exists (Workers, and `vite dev` through the adapter's platform proxy). Entries are JSON under the synthetic key `https://cache.midb.internal/<encoded key>` with a `Cache-Control` `max-age` of the entry's TTL and an expiry header. Values must survive `JSON.stringify` (one that does not is not stored). The write runs through `waitUntil`, after the response. The Cache API is per data centre, so a value cached by one isolate serves the next one there. A Cache API error is a miss.
  - **A per-isolate memory level** (`memory.ts`) in front of it: a bounded LRU with TTLs that answers repeats without a Cache API call, and takes only the TTL an entry has left when it is filled from the Cache API.
  - **Memory alone** where `caches` is missing (unit tests, plain Node).
- **Counters.** `incr(key, ttlMs)` adds 1 to a fixed-window counter and returns the count; the window starts on the first hit and the count starts over when it ends. Counters always live in the memory level (a separate `Map`, oldest window dropped first), so counters and cached values never evict each other; the Cache API has no atomic increment. They are the fallback of `rateLimit` where a bucket has no binding.
- **Keys** are namespaced: `tmdb:movie:v2:<id>`, `tmdb:series:v2:<id>`; `tmdb:search:v1:<lowercased query>`; `ddd:imdb:<id>`, `ddd:tmdb:<id>`; `catalogue:counts`, `catalogue:hero-pool:v2:<pool>` (the landing's database queries), `source-sync:dates` (the sync times); counters `rl:<bucket>:ip:<address>` / `rl:<bucket>:user:<id>`. The TTLs are in `integrations/tmdb/client.ts`, `integrations/ddd.ts`, `data/catalogue.ts` and `data/source-sync.ts`. Cache API entries outlive a deploy, so a change to a cached value's shape bumps its key's version (`v2` in the TMDB keys).

## Auth flow (Better Auth)

1. **Better Auth** runs in the Worker. `getAuth()` (`#lib/server/auth/auth.ts`) builds it once per isolate from `createAuth` (`create-auth.ts`) with the Worker's env: the D1 adapter over `#lib/server/db.ts`, `PUBLIC_ORIGIN` as base URL, trusted origin and passkey RP origin (the RP id is its hostname), and `BETTER_AUTH_SECRET`. Its telemetry is off, its own rate limiter is off (it counts per isolate), and the client IP comes from `cf-connecting-ip`.
2. **Sign-in methods.** Google and Discord are enabled only when their client id and secret are set. Passkeys (`@better-auth/passkey`) need no secret and work on `localhost`. Sign-up with a passkey alone is allowed: `registration.requireSession` is false, `resolveUser` (`passkey-signup.ts`) hands out a fresh id, and `afterVerification` creates the user with the placeholder email once the passkey verifies. Every new account, on any sign-up path, gets a generated username (`databaseHooks.user.create.before` in `create-auth.ts`): a name from `FEMINIST_ICONS` (`#lib/media/utils/feminist-icons.ts`), `_` and four random digits, drawn again on a collision a bounded number of times and failing the sign-up after that (`generate-username.ts`). `USERNAME_RE` lives in `#lib/media/utils/username.ts`. The reader changes it on `/user/profile`. When `TURNSTILE_SECRET_KEY` is set, `guardPasskeySignUp` (`turnstile.ts`, a `hooks.before` step) verifies the token with Cloudflare's siteverify (secret, token and client IP, as Better Auth's captcha plugin does) on `/passkey/generate-register-options`, only when there is no authoritative session: a sign-up needs the token, a signed-in reader adding a passkey does not. It is skipped when no secret is set. `allowUnlinkingAll` is on because Better Auth's own last-account check counts accounts only; `guardLastMethod` (`last-method.ts`) counts accounts and passkeys together and refuses to remove the last one, for `/unlink-account` and `/passkey/delete-passkey` alike, and answers UNAUTHORIZED when the database has no live session (a revoked browser may still hold a cached `session_data`). Without `BETTER_AUTH_SECRET`, `createAuth` starts only on a localhost origin: Better Auth's own check keys on `NODE_ENV`, which a Worker does not set. Linking is on for Google and Discord with `allowDifferentEmails`, so a passkey-only account can link a provider; `adoptProviderEmail` then adopts the provider's verified email. Only Google is in `trustedProviders`: a Discord sign-in links to an existing user only when Discord reports the email verified. `account.encryptOAuthTokens` stores the access and refresh tokens encrypted with a key derived from `BETTER_AUTH_SECRET`; `adoptProviderEmail` decrypts them with Better Auth's `decryptOAuthToken` before the provider reads them.
3. **Route.** `src/routes/api/auth/[...all]/+server.ts` runs `rateLimit(event, 'RL_AUTH')` on the client IP, then `getAuth().handler(request)`, and makes the response private with `asPrivate` (`#lib/server/http/cache.ts`, the helper the hook's `withSafeCacheHeaders` uses too): `private, no-store`, no edge directive, cookies kept.
4. **Cookies.** Better Auth sets `better-auth.session_token` (Better Auth's default session length, `HttpOnly`; `__Secure-` prefixed on HTTPS), `better-auth.session_data` (the signed session cache, `session.cookieCache.maxAge` in `create-auth.ts`; the hook's session read cannot set cookies, so it never renews it) and, during a passkey ceremony or an OAuth round trip, short-lived challenge and state cookies. No cookie is readable by page scripts.
5. **The hook** (`src/hooks.server.ts`). `locals.getUser()` is lazy and memoised per request: `getAuth().api.getSession({ headers })`, then `getUserById`; it returns the `UserRow`, or `null` without a session, for a deleted user and for a banned one. Only `/api/me`, `/user/*` loads, actions and endpoints and the moderation gate call it; public loads never do.
6. **Gates.** The hook gates `/user` and `/user/*` (not `/users…` or `/username`) on the presence of the session cookie (`getSessionCookie` from `better-auth/cookies`, which accepts the `__Secure-` name): no cookie → `303 /auth`, returned through `withSafeCacheHeaders` so it is never cached. The cookie is not proof of a session, so every load, action and endpoint still calls a guard. `/user/moderation*` additionally awaits `requireRole(locals, ['moderator', 'administrator'], { page: true })` → `error(403)` for other roles.
7. **Guards** (`#lib/server/auth/guards.ts`): `requireUser(locals, { page? })` returns the `UserRow` or throws (`redirect(303, '/auth')` for page loads, `error(401)` otherwise); `requireRole(locals, roles, { page? })` adds `error(403)`. Every `/user/*` load, action and endpoint calls one; nothing reads a user off `locals` directly. Form actions on public pages are not under the `/user` prefix, so the guard is their only check.
8. **SSR is user-agnostic.** There is no root `+layout.server.ts`; public pages carry no user data and are CDN-cacheable (see _Caching policy_). The `/user` layout returns `{ me: PublicUser }` with `private, no-store`.
9. **Orphans.** D1 has no transaction around the passkey insert, so a failed sign-up can leave a user with no `account`, no `passkey` and no `session`. `pnpm db:cleanup:orphans [--local|--remote]` deletes exactly those users once they are older than `ORPHAN_AFTER_MS`. The `cleanup` job of `deploy.yml` runs it daily (see Deploy).
10. **Client.**
    - `#lib/auth-client.ts` is the Better Auth client (`authClient`) with `passkeyClient`; `createCaptchaClient(token)` adds the Turnstile token for passkey sign-up, because `addPasskey` sends no per-call headers on the request the check guards. A new passkey is named from the browser and system (`deviceName.ts`) through `addPasskey({ name })`.
    - `/user/security` shows each result beside its action (in the row's plate, or under the add and link buttons), moves focus into an opened plate and back to its trigger on close, and goes through `auth-errors.ts` for every failure. `/auth` and `/user/security` render in the browser and take their provider list and icons from `#lib/media/utils/auth-providers.ts`. Which social buttons exist comes from their loads (`configuredProviders()`), not from a `PUBLIC_*` value: `/auth`'s load sets `private, no-store` and never reads the user, so the page keeps its cache policy.
    - `/auth` renders its form once it knows whether the browser offers passkey autofill and that the reader is not signed in (the session rune; a signed-in reader is redirected to `/user/profile`), so no field appears after the buttons. A Turnstile token is single-use, so a failed or cancelled sign-up resets the widget; when the check cannot run, the sign-up button runs it again, and the passkey prompt is never asked for without a token while a site key is set. A dismissed prompt arrives from Better Auth's client as `ERROR_PASSTHROUGH_SEE_CAUSE_PROPERTY` without its cause, so `auth-errors.ts` reads the browser's message too. With the widget, the passkey prompt starts on a click after the check passes (browsers want a fresh click for it), or at once while the original click still counts as user activation.
    - `session.svelte.ts` keeps `midb_hint=1` (readable, `SameSite=Lax`, `HINT_MAX_AGE_SECONDS` long, `Secure` on HTTPS, no identity). It is set when `/api/me` or the `/user` layout reports a user and cleared by `clear()` and when `/api/me` answers null; an unanswered `/api/me` leaves it. It only picks the navbar's first-paint placeholder; the server never reads it.

## Caching policy

Workers Caching (`"cache": { "enabled": true }` in `wrangler.jsonc`) is the CDN. Cloudflare answers a hit before the Worker runs, so the code only sets headers. The key is path plus query plus the Worker version, and **cookies are not in it**: a deploy starts with an empty cache, and a response that depends on the reader would be served to everyone. A response with `Set-Cookie`, `private` or `no-store` bypasses the cache. A 200 with no cache header is cached by default, which is why the hook below exists. A policy applies to successful responses only: a load sets it after its lookup succeeds, because Kit applies `setHeaders` to the error page and the error `__data.json` too.

- `#lib/server/http/cache.ts` holds the policies as header sets, so they are greppable. A browser `Cache-Control` and an edge `CDN-Cache-Control` (which overrides `Cache-Control` at the edge only) are spread into `setHeaders`, or into a response's `headers`.
- `PUBLIC_PAGE` (a browser `Cache-Control` that revalidates, and an edge `CDN-Cache-Control` with stale-while-revalidate) is set by the `/resources`, `/movie/[movieId]` and `/tv/[seriesId]` loads; it applies to both the HTML and `__data.json`.
- `PUBLIC_NO_STORE` (`no-store`) is set by `/`: user-agnostic, but its hero films are random per request, so no cache keeps it. The expensive part, the film pool and the counts, is cached in the server cache (`catalogue.ts`).
- **Rule:** a load that sets `PUBLIC_PAGE` must not depend on the request's user (no `locals.getUser()`). The cache key ignores cookies, so anything user-specific would be served to every visitor. Signed-in readers get the same cached HTML; the navbar hydrates from `/api/me`.
- `PUBLIC_SEARCH` (a browser and a longer edge TTL, the edge matching the server-side search cache) is set by `/api/search` on a successful result: the response is user-agnostic, so the edge absorbs repeated queries. An error answer (TMDB down, network failure) and a 429 carry no policy, so the hook makes them `private, no-store`.
- `PUBLIC_COMMENTS` is set by `GET /api/titles/[kind]/[tmdbId]/comments` with `Cache-Tag: comments:<kind>:<tmdbId>` (`commentsHeaders`): the browser revalidates, the edge keeps the list for a short TTL. Comment writes, edits, deletes and moderator actions purge the tag with `cache.purge({ tags })` inside `waitUntil` (`purgeTitleComments`); a failed purge is logged and swallowed. Votes do not purge, so a score can trail by up to one TTL. The signed-in reader's votes and unpublished comments come from `GET …/comments/viewer`, which is `PRIVATE_NO_STORE`.
- `PUBLIC_READER_REPORTS` is set by `GET /api/titles/[kind]/[tmdbId]/reports` with `Cache-Tag: reports:<kind>:<tmdbId>` (`readerReportsHeaders`), under the same TTLs as the comment list. A report write or delete purges the tag (`purgeTitleReports`). A report that starts counting by itself (its account reaches `REPORT_ACCOUNT_MIN_AGE_DAYS`) does not purge, so the counts can trail by up to one TTL. The reader's own report comes from `GET …/reports/viewer`, which is `PRIVATE_NO_STORE`.
- `PUBLIC_IMAGE` is set by `/img/tmdb/*` on a success: a poster file never changes under its name, and its TTL stays under TMDB's cap on caching its images.
- `PRIVATE_NO_STORE` (`private, no-store`) covers personalised responses: `/api/me` and every `/user/*` page (set in the `/user` layout).
- **Safe default** (`hooks.server.ts`, `withSafeCacheHeaders`): a response without `cache-control` becomes `private, no-store`, and a response with `Set-Cookie` is forced to `private, no-store` with any `CDN-Cache-Control` removed. Every branch that forces `private, no-store` also removes `CDN-Cache-Control` and `Cloudflare-CDN-Cache-Control`. The hook's own `/user` redirect to `/auth`, and the `/user/moderation` guard's redirect or error, are returned through it, not thrown, so they are never cached either. A route opts in to caching by setting a policy; forgetting to never publishes it.
- Workers Caching has no local emulation: `vite dev` and the built Worker under `pnpm preview` (`wrangler dev`) send the headers but cache nothing, so a hit can be checked only on a deployed Worker.
- **Rate limiting** (`#lib/server/http/rate-limit.ts`): `rateLimit(event, bucket, { userId? })`, where `bucket` is a `RateLimitBucket` naming a Workers rate-limit binding (`RL_SEARCH`, `RL_AVAILABILITY`, …; `limit` and `period` are in `wrangler.jsonc`). It throws `error(429)` when the binding says `success: false`. It keys on `userId` when the route already has the user (after `requireUser`), else on `event.getClientAddress()`, and never reads the user itself, so CDN-cached routes stay user-agnostic. Applied to `/api/search` (`RL_SEARCH`, after the empty-query short-circuit), `/user/profile/availability` (`RL_AVAILABILITY`, per user) and the comment writes (`RL_COMMENT`, `RL_VOTE`, `RL_REPORT`, per user), the reader-report writes (`RL_CONTENT_REPORT`; the counts flag uses `RL_REPORT`, per user) and the moderation actions (`RL_MODERATE`, per user). The binding counts per location and is eventually consistent, so a limit is approximate. A bucket with no binding (unit tests, a dev setup without one) falls back to the memory `incr` with the same numbers (`FALLBACK_LIMITS` in `rate-limit.ts`), per isolate. A binding error lets the request through.
- User-specific bits on a public page (e.g. a future "your rating") go in a separate uncached fetch, the same way the navbar uses `/api/me`.

`src/env.ts` marks every `PUBLIC_*` value `static`, so the app uses the build environment's value, inlined at build time; the `wrangler.jsonc` `vars` copies must match it, and changing one means a rebuild. The database is the `DB` binding, so `build` and `check` need no database and the server bundle contains no connection string. Secrets and bindings are read through `#lib/server/env.ts` over `cloudflare:workers`: `wrangler secret put` in production, `.env` in `vite dev` (the adapter's platform proxy loads it through Wrangler). `wrangler dev` (`pnpm preview`) reads `.dev.vars` when it exists, else `.env`; `.dev.vars` replaces `.env` rather than adding to it, and neither reads the process environment. `wrangler.jsonc` holds the bindings and non-secret `vars`, no secrets; `pnpm cf:types` regenerates `worker-configuration.d.ts` from it. `.env.example` is the committed template (allow-listed in `.gitignore`) and lists every variable. Its placeholders are valid enough for `pnpm check` and `pnpm build`, so a fresh clone and CI only need `cp .env.example .env`. Title pages need real `TMDB_API_TOKEN`/`DDD_API_KEY` values. Passkey sign-in needs no secret on `localhost`; Google and Discord need their client ids and secrets. Deploys: see Deploy.

**One package manager.** pnpm 10.28 locally and in CI: `package.json` declares `"packageManager": "pnpm@10.28.0"` and `"engines": { "node": ">=22.18" }` (the first Node 22 with type stripping on; `.npmrc`'s `engine-strict=true` enforces it), so CI installs exactly the `pnpm-lock.yaml` it tests. `pnpm.overrides` in `package.json` pins most direct dependencies to an exact version, so bumping a pinned one means editing its override (a `devDependencies` range bump alone changes nothing there; a dependency with no override follows its range); `pnpm.onlyBuiltDependencies` lists `esbuild` and `workerd`, the dependencies whose build scripts run (pnpm 10 blocks the rest). The old `npm install --legacy-peer-deps` was hiding a real peer conflict (Storybook 9 peers on Vite ≤7 and vite-plugin-svelte ≤6), fixed by moving to Storybook 10.6. No dependency is pinned to `latest`.

### Local run sequence

```bash
pnpm install
cp .env.example .env
pnpm db:migrate:local    # creates the local D1 in .wrangler/state
pnpm db:sync:all --local   # Unconsenting Media, Bechdel Test, TMDB ids and popularity (--fixtures: offline)
pnpm dev                # vite dev, with the Worker's bindings emulated
pnpm preview            # builds, then runs the built Worker locally with `wrangler dev` on 4173

pnpm test:db          # wipes .wrangler/test-state, migrates it from zero, runs *.db.spec.ts
```

### npm scripts

`dev` · `build` · `preview` (`pnpm build && wrangler dev`, local only, port 4173) · `check` · `typecheck` · `test` = `test:integration` + `test:unit` · `test:unit` = `vitest --project unit` (no DB) · `test:db` = `vitest run --project db` (local D1, no Docker) · `lint` / `lint:fix` / `format` (what they run: `package.json`, AGENTS.md) · `storybook` / `build-storybook` · `db:generate` · `db:migrate:local` · `db:migrate:remote` · `db:sync:um` · `db:sync:bechdel` · `db:sync:popularity` · `db:sync:all` · `db:backfill:tmdb` · `db:seed:admin` (`--username` or `--email`, case-insensitive promote to administrator). The `db:sync:*` and `db:backfill:tmdb` scripts take `--local` (default) or `--remote`; the sync scripts also take `--fixtures`, and `db:sync:bechdel` `--full`.

### CI (`.github/workflows/tests.yml`)

Runs on every PR, on pushes to `main`, and on manual dispatch. Every job but `commits` installs pnpm (the `packageManager` version) and Node 22 with the pnpm cache.

- **`static`**: `pnpm install --frozen-lockfile` → `cp .env.example .env` (so the static variables in `src/env.ts` resolve) → `pnpm check` → `pnpm typecheck` → `pnpm lint` → `pnpm build`.
- **`unit`**: `pnpm install --frozen-lockfile` → `cp .env.example .env` (the SvelteKit plugin validates the static variables when Vitest loads the config) → `pnpm test:unit --run`. Needs no secrets or database, because unit specs mock `$app/env/*` and `#lib/server/db.ts`, and take `cloudflare:workers` from a stub.
- **`migrations`**: `pnpm exec drizzle-kit generate --name drift_check`, then fails (printing the status and diff) if `git status --porcelain db/migrations` is non-empty. Needs no DB. A drizzle-kit prompt also fails it (no TTY), which is the correct outcome.
- **Sync workflow**: `sync-sources.yml` is separate from `tests.yml`; see Source sync, Schedule.
- **`db`**: `cp .env.example .env` (as in `unit`), then `pnpm test:db` on a local D1, with no service and no secrets. Global setup migrates the empty database from zero, so this job also proves the migration chain applies cleanly.
- **`e2e`**: runs on every event, forks included, and needs no account. It runs `db:migrate:local` and `db:sync:all --local --fixtures`, writes `.dev.vars` (where `wrangler dev` reads the Worker's vars, overriding `wrangler.jsonc`: `PUBLIC_ORIGIN`, fake Google and Discord client values, and `TMDB_API_TOKEN`), then `pnpm test:integration --trace off`; `playwright.config.ts` starts `pnpm preview` (build with the job's `PUBLIC_*` values, then `wrangler dev`). `TMDB_API_TOKEN` is the one secret, handed to the step that writes `.dev.vars`; on a fork pull request it is empty and the specs that need TMDB skip. The Playwright report is uploaded on failure.

### Deploy (`.github/workflows/deploy.yml`)

Every job that holds a Cloudflare token runs only on the canonical repository. The `PUBLIC_*` values are inlined into the build and must equal the `vars` of the target in `wrangler.jsonc`. The origin and the Turnstile site key come from repository variables (`PUBLIC_ORIGIN` and `PUBLIC_TURNSTILE_SITE_KEY` for production; `PREVIEW_ORIGIN` and `PREVIEW_TURNSTILE_SITE_KEY` for the preview), and the TMDB values are read from `wrangler.jsonc`. Both deploy jobs run `scripts/ci/public-vars.ts` before the build: `export` writes the TMDB values into the job's environment, and `check` fails the run when any `PUBLIC_*` value of the build differs from the target's `vars`. `tests.yml`'s `e2e` job reads the TMDB values the same way.

- **`production`** (push to `main`, or a manual run on `main`; environment `production`): build, log the D1 Time Travel bookmark (`wrangler d1 time-travel info DB`), `wrangler d1 migrations apply DB --remote` (a failure stops the job before the deploy), then `wrangler deploy`. Both d1 commands and the deploy pass `--env ""`, which targets the top-level configuration, because `wrangler.jsonc` also defines `preview`. Runs never overlap and a running one is never cancelled half-way through a migration; a run waiting behind it is replaced by a newer waiting run.
- **`preview`** (a pull request whose head is in this repository, not Dependabot's; environment `preview`): build with `PREVIEW_ORIGIN`, migrate the preview database (`--env preview`), then `wrangler deploy --env preview`, so the latest pull request is live at `PREVIEW_ORIGIN` with full sign-in. Each pull request has its own concurrency group (`deploy-preview-<number>`, never cancelled); the preview Worker and its database are shared, so previews from several pull requests overwrite one another and the latest push wins. A fork pull request does not match the condition and has no secrets; `pull_request_target` is never used.
- **`cleanup`** (daily schedule): `pnpm db:cleanup:orphans --remote`, with the three `CLOUDFLARE_*` values the remote scripts read.
- A migration must work with the Worker version still serving (`.claude/rules/code-standards.md`, Database).
- Both Workers run on Workers Paid (D1 Time Travel keeps 30 days there) with Workers Logs on (`observability` in `wrangler.jsonc`, which `env.preview` inherits).
- The Cloudflare token and account id are the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, passed only to the steps that call wrangler. The Worker's own secrets are set with `wrangler secret put` (add `--env preview` for the preview Worker), never by the workflow.

## Testing

Three layers, plus Storybook for component development. Specs live in a `__tests__/` folder next to the code they cover; Playwright specs in top-level `e2e-tests/`.

- **`unit`** (Vitest project, `jsdom`; `pnpm test:unit`): `src/**/*.{spec,test}.{js,ts}`, `db/**/*.spec.ts` and `scripts/**/*.spec.ts`, minus `*.db.spec.ts`. Needs no database or secrets, and a `.env` copied from `.env.example` for the static variables: specs mock `$app/env/*` and `#lib/server/db`, set secrets and bindings on the `cloudflare:workers` stub (`src/test/cloudflare-workers.stub.ts`), the TMDB/DDD `fetch` and `$app/*` as needed. Components render through `@testing-library/svelte` (`svelteTesting()` in `vite.config.ts`) with `@testing-library/jest-dom` matchers. Rune classes (`TitleView`, `EpisodeFilter`, `Session`, `MovieSearchState`, `DebouncedQuery`) are tested directly, with fake timers where they debounce. Endpoints are called as plain functions with a hand-built `RequestEvent` (`src/__tests__/api-*.spec.ts`).
- **`db`** (Vitest project, `node`; `pnpm test:db`): every `*.db.spec.ts` against a local D1 (Miniflare, through wrangler), with no Docker and no secrets. The project has its own config in `vite.config.ts` and does not extend the root one: the Svelte plugins add the `browser` export condition, which makes Miniflare load the browser build of `ws`. `db/test/global-setup.ts` wipes `.wrangler/test-state` and applies `db/migrations` to it with `wrangler d1 migrations apply --local` once per run (so the job also proves the baseline applies from zero); `db/test/setup.ts` opens that state with `getPlatformProxy`, binds the app's `db` to it (`bindDb`), deletes every table's rows in foreign-key order before each test and disposes the proxy after. `getPlatformProxy` takes the state root itself while the wrangler CLI adds a `v3` folder, so the setup passes `.wrangler/test-state/v3`. Files run serially (`fileParallelism: false`). "Never writes" checks use `db/test/writes.ts`, whose triggers log every write to a test-only table. Covers title resolution, sources, UM candidates, user queries, community-table constraints, the D1 behaviours the app relies on (`db/test/d1.db.spec.ts`) and the source sync on trimmed fixtures (`db/test/fixtures/`).
- **`e2e`** (Playwright, `pnpm test:integration`): `playwright.config.ts` runs `pnpm preview`, which serves the built Worker with `wrangler dev` on 4173 (Node's `vite preview` cannot load the built Worker: it imports `cloudflare:workers`), with one worker, because the specs share one local D1 and `RL_AUTH` counts sign-ups per address (the comment limits count per user). A local run needs `.dev.vars` with `PUBLIC_ORIGIN=http://localhost:4173` and the migrated, fixture-loaded local D1 (CI shows the sequence); the build takes `PUBLIC_ORIGIN` and an empty `PUBLIC_TURNSTILE_SITE_KEY` from the environment. `support/` holds the helpers: `env.ts` reads `.dev.vars` (so a spec skips exactly when the Worker lacks a value, and `hasTmdb` gates every spec that needs TMDB), `db.ts` seeds a title row and promotes a moderator through `wrangler d1 execute --local`, and `passkeys.ts` adds a Chromium virtual authenticator over CDP and signs up with a passkey. Specs: `landing`, `navbarSearchOverflow` (`/api/search` mocked with `page.route`), `cacheHeaders` (the exact `Cache-Control`, `CDN-Cache-Control` and `Cache-Tag` of public pages, `__data.json`, the comment list and images, and `private, no-store` on `/api/me`, `/api/auth/*`, the viewer endpoint and `/user/*`), `passkeys` (sign-up, sign-out, sign-in, and the navbar showing the account on a public page after sign-in), `oauth` (the Google and Discord buttons redirect to their providers; the request is aborted), `titles` (search, film and series pages, the poster route) and `comments` (a pending comment visible only to its author until a moderator approves it, through the endpoints without TMDB and through a film page with it). Workers Caching and `cache.purge` are not emulated by `wrangler dev`: a purge logs `cache.purge is not a function` and is swallowed, and a cache hit is checked on a deployed Worker.
- **Storybook** (`pnpm storybook`, `build-storybook`): `*.stories.svelte` with `@storybook/addon-svelte-csf`. Only the poster `image` story remains after the redesign deleted the unused primitives. Not run in CI.
- **Rule of thumb** (`.claude/rules/code-standards.md`, Testing): anything that touches the database gets a `*.db.spec.ts`; everything else stays in `unit` and mocks the DB. Moving a function means moving its spec's import too.

### Verification baseline

The baseline every finished task reports is `.claude/rules/code-standards.md`, Checking a change. CI runs the same jobs (see _CI_), plus the drift check (`pnpm exec drizzle-kit generate --name drift_check` → no change) and, on pull requests, the commit-subject check.
