# Privacy

MIDB has no trackers, analytics or advertising, and sells or shares no data. This file says what the site stores and sends today. It changes in the same commit as any change to what the code stores or sends (`.claude/rules/code-standards.md`, Making a change).

## Reading the site

A reader who does not sign in gives MIDB no personal data.

- **The browser stores** one value: the chosen theme, in `localStorage` (`theme`). It never leaves the browser.
- **Third-party requests** from the browser: none. Posters load from MIDB's own `/img/tmdb/` path, and the Inter Tight font is served from MIDB.
- **MIDB's own server** looks up each page's data on TMDB and Does the Dog Die, and fetches each poster from `image.tmdb.org` (TMDB). These requests carry the title or file being looked up, never anything about the reader, so TMDB sees MIDB's server and not the reader's IP address or browser.
- **Hosting.** The site runs on Cloudflare Workers, which keeps standard request logs (IP address, URL, time) under its own policy. MIDB turns on Workers Logs, which stores each request's metadata and the server's error messages in the Cloudflare account for the retention Cloudflare sets; the error messages name the failing step (a cache, a source, the rate limiter) and never a reader's account, cookie or comment. MIDB's database is Cloudflare D1, so the account data listed under Signing in is stored by Cloudflare. D1 Time Travel keeps the database's history for the window Cloudflare sets (30 days on the paid plan, per Cloudflare's D1 documentation), so a deleted account stays recoverable from that history for that long. The server also caches what it fetches from TMDB, Does the Dog Die and its database, search results, public pages and posters, in Cloudflare's cache. These hold film data and search text, never a reader's IP address, cookie or account.
- **Source sync.** A scheduled job, not a page visit, reads public data from unconsentingmedia.org (the Unconsenting Media list), bechdeltest.com (year pages and the feed of recent additions) files.tmdb.org (TMDB's daily id exports) and api.themoviedb.org (TMDB id lookups by IMDb id, with MIDB's TMDB API token). These requests send no reader data, only the `MIDB-sync` User-Agent, which names the project's repository, and the token on the TMDB lookups.
- **Rate limiting.** The rate limiter sends a key to Cloudflare's rate-limit service and counts it for the window set in `wrangler.jsonc`: the reader's IP address for search and sign-in, or the account id for the username check.

## Signing in

Accounts are handled by MIDB itself with Better Auth, which runs inside MIDB's Worker and database. There are no passwords.

- **Sign-in methods:** a passkey, or a Google or Discord account where the site offers them. Google or Discord receive a sign-in request when that method is used, and tell MIDB the account's name, email address and picture.
- **MIDB's own database** (Cloudflare D1) stores, for each account:
  - the account id, a display name, and the email address (a passkey-only account has a placeholder address under `users.invalid` that is never shown or used);
  - the role (user, moderator or administrator) and any ban or mute;
  - the username and avatar the account holder picks (a new account starts with a generated username, a feminist figure's name and four digits, which the account holder can change);
  - each linked Google or Discord account: the account id, a display name, the email address, and the picture URL Google or Discord sent; the access and refresh tokens it returned, encrypted with a key derived from the site's secret; the ID token; their expiry and the granted scope;
  - each passkey: its public key and credential id, a label, the authenticator model (AAGUID), its type, whether it is backed up, its transports, a use counter, and when it was made. The private key stays on the reader's device. A new passkey is labelled with the browser and system it was made on, such as "Chrome on macOS", until the account holder renames it;
  - each session: a token, its expiry, the IP address and browser that started it.
- **Cookies:** `better-auth.session_token` identifies the session and lasts seven days. `better-auth.session_data` holds a signed copy of the session for five minutes, so a request within that time skips the session lookup. A passkey or Google or Discord sign-in sets one more short-lived cookie while it runs. None of these can be read by page scripts. On HTTPS each of these names starts with `__Secure-`. `midb_hint` is a separate cookie that page scripts set while a reader is signed in, for seven days. Its value is `1`: it holds no identity, the server does not read it, and the page only uses it to draw the account button before the account is known. Signing out removes it.
- **Bot check:** creating an account with a passkey can require a Cloudflare Turnstile check, which sees the reader's browser and IP address. Cloudflare's script loads from `challenges.cloudflare.com` only when a reader starts creating an account on the sign-in page, and only when a Turnstile site key is configured; no other page loads it.

The email address is shown only on the account's own profile page. Other readers see only the username and avatar. The username, generated or chosen, is public on the account's comments. Signing out ends the session and clears the cookies. Better Auth's telemetry is off, so nothing about the site is sent to its authors.

## Ratings and comments

Community ratings are not submitted yet. Comments and community reports are submitted through the site's own endpoints, by a signed-in account that is not muted or banned.

- **What MIDB stores for a comment:** its text, the account that wrote it, the film or series it is on, the comment it answers if it is a reply, when it was written and last edited, its status (awaiting review, published, hidden, rejected or deleted), and the reason for a hide or a rejection, or why the site's checks gave it that status. Editing replaces the text; the earlier text is not kept. Deleting a comment marks it deleted and keeps its row and its text, with no time limit, so replies stay in their thread. Other readers no longer see the text. The author still sees it on the comment history page, and moderators see it in the action log and in the All comments table, which lists every comment in any status, deleted ones included, with its text, the author's username, the automatic check's result and the newest scan label.
- **Automatic check:** a new or edited comment is checked before it is stored with a status. The site sends Anthropic (the Claude API) the comment text, the title's name and, for a reply, the text of the comment it answers. It does not send the email, the username or any account id. Anthropic processes it under its own terms. MIDB stores the verdict beside the comment (the decision, categories, severity, a reason of at most `MODERATION_REASON_MAX` characters, the model's name), or the code of a failed check, and nothing else of Anthropic's answer. Without an `ANTHROPIC_API_KEY` nothing is sent: a comment the blocklist matches is rejected and every other comment waits for a moderator.
- **Votes and reports:** each up or down vote is stored with the account and the comment, so a vote can be changed or removed. A report stores the account, the comment, a reason and an optional note. Enough open reports from different accounts (`REPORT_THRESHOLD` in `src/lib/media/utils/comments.ts`) send a published comment back to review.
- **Staff checks:** moderators and administrators can run two more checks with Claude Haiku 5.5 (Anthropic) from the moderation table. An AI search sends the moderator's query text and today's date. A scan sends the text of the comments on the moderator's page that are not deleted, each comment's film or series name and kind, and the moderator's scan text. The site adds no email, username or account id to either request; the query and the scan text are sent as the moderator typed them. Anthropic processes it under its own terms. Each scan stores a label for every comment the model answered, beside the comment: the scan text, whether the comment matched, the categories, a severity, a reason, the model's name, which staff account ran it and when. Earlier labels are kept. A label is deleted with the comment's row, which goes only when the comment's account or title is removed from the database; a comment its author deleted keeps its row, so its labels stay. If the staff account is deleted, the label stays and no longer names it. An AI search stores nothing. Without an `ANTHROPIC_API_KEY` neither check runs and nothing is sent.
- **MIDB community reports:** a report is stored with the account that made it and the film or series, its answers (each level, the Unconsenting Media concern flags when sexual violence is answered Present, and the optional framing, with a missing answer meaning not sure), its status (counted, waiting for review or rejected), the reason it was held, and when it was made and last edited. There is one per account per title; editing replaces the answers, and deleting removes the row. A "Counts look wrong" report stores the title, the account, an optional note, its status (open, resolved or dismissed), the moderator who closed it and the times.
- **Moderation log:** each moderator action (approve, hide, reject, restore, dismiss, mute, ban, and on community reports: count or reject a report, reject all of an account's reports, resolve or dismiss a "Counts look wrong") is stored with the moderator, the comment, account or title it applied to, a reason, the length of a mute and the time. It stays after what it applied to is removed.
- **Who sees what:** everyone sees the published comments of a title, with the author's username and avatar and the comment's score; a comment that is not published is not shown, though a placeholder with no text and no author stays where it has published replies. The author sees their own comments in every status, and the reason for a rejection. Moderators see the queue (each comment with its author's username and avatar, how many comments the account has written, when the author's mute ends, and the open reports on it with their reasons, notes and the username of the account that made each), the log, and the All comments table, which lists every comment in any status, deleted ones included, with its text, the author's username, the automatic check's result, the newest scan label and the username of the account behind each open report. Reports and votes are not shown to other readers. A title page shows community reports only as counts, with no account named: the number of counted reports, and counts per answer once enough reports count. An account's public profile names the titles its counted reports are on, with no date and no answers, and shows its published comments (text, film or series, date, whether edited, score, and the author of the published comment a reply answers), its join day and its comment score total. The author sees their own report and its status. Moderators see each community report with its account's username, account age, report count and comment count, and each "Counts look wrong" with its note and the username of the account that raised it.
- **Public profile:** every account with a username has a page at `/u/<username>` that anyone can open, signed in or not. It shows the username, the avatar, the day the account was made (no time), "Moderator" or "Administrator" for a staff account, the sum of the scores of the account's published comments, those comments (text, film or series, date, whether edited, score, and the author of the published comment a reply answers) and the film or series of each community report that counts, which is the same rule as a title's counts. A title page shows community reports only as counts; the profile names the titles an account's counted reports are on, with no date and no answers. It shows no email, no comment that is not published, no moderation reason or status, no votes and no report answers. A banned account and an account with no username have no page.
- **Caching:** the published list of a title is kept by Cloudflare's cache for a short time and cleared when someone comments, edits or deletes, or a moderator acts (`src/lib/server/http/cache.ts` holds the times). Scores can lag by that time. A title's community report counts are cached the same way under their own tag, and cleared when a report is saved or deleted or a moderator acts on one. A public profile is cached under the account's own tag and cleared by the same writes, a username or avatar change, a mute and a ban, and, when a comment enters or leaves the published list, for the authors of its published replies, whose profiles name it. Comment scores and the score total, which votes change, can lag by the cache time, and so can the list of counted reports when an account becomes old enough to count or a mute ends. Author links in cached title comment lists can point at an old username for the cache time after a rename, and a role change is not purged. The list and the counts carry nothing about the reader who requests them.
